# CLAUDE.md — Hwy4Events

Community events site for the Highway 4 corridor (Angels Camp to Bear Valley, CA). Next.js app deployed on Vercel, data in Supabase.

## Tech Stack

- **Framework:** Next.js 16 (App Router) + React 19 + Tailwind v4
- **Database:** Supabase project **`uzediwokyshjbsymevtp`** — the shared rob-ai / PAOS project (org "Gabel.Global", labeled "Claude Code" in the Supabase dashboard, **not** a separate hwy4 project). Reachable via the Supabase MCP (`apply_migration` / `execute_sql` with that project_id). Tables: `hwy4_events`, `hwy4_orgs`, `hwy4_venues`, `hwy4_artists`, `hwy4_sources`, `site_config`, `event_submissions`, `analytics_daily`.
- **AI:** Anthropic SDK (Claude Opus) for daily briefing generation
- **Maps:** Leaflet / react-leaflet
- **Hosting:** Vercel (auto-deploys from main branch)

## Architecture

- Events are scraped externally and loaded into Supabase — this app is **read-only** against event data (except community submissions via `/submit`)
- Community submissions land in `event_submissions` (status `pending`). Review and publish them at **`/admin/submissions`** (see `PRD-admin-submissions.md`): **Publish** inserts a `community_sourced` `hwy4_events` row (`source_name='Community Submission'`, `visibility='public'`, `status='confirmed'`, a `dedup_key` from the shared `generateDedupKey` in `lib/event-identity.ts`) and flips the submission to `approved` (recording `published_event_id`); **Dismiss** sets it `rejected`. `community_sourced=true` renders a pine **"Community sourced"** badge on the event card and detail page. **The publish path runs the shared write-time machinery (2026-07-28).** It used to raw-insert the reviewer's form fields, making it the one writer that skipped everything `upsertEvents` does for a scraper: no venue resolution (so a community row entered with `venue_key IS NULL` and no address, stripped of the strongest dedup signal there is) and no duplicate check beyond the `dedup_key` unique index, which only catches a byte-identical re-listing. Now `publishSubmission` (a) resolves the venue against `hwy4_venues` via `matchVenueRow` ([lib/venue-match.ts](lib/venue-match.ts), the app-side registry lookup — `tsconfig.json` excludes `scripts/`, so the scraper's matcher can't be imported; an ambiguous name resolves to null rather than guessing a key that would assert a shared room) and stamps `venue_key` + the registry address, and (b) **refuses to publish a row the shared `isSameEvent` reads as an event already listed**, naming it and pointing at Merge. The block is overridable by a "Publish anyway" checkbox, because the matcher is a heuristic and the reviewer is the authority; what must not happen is publishing a duplicate *silently*.
- **Submission triage (agent advisory, Stage 1 of the Agent Cockpit).** Every new submission is auto-researched by an agent (`lib/agent/submission-triage.ts`): it checks the DB for an existing match with the shared `isSameEvent`/`generateDedupKey` matcher (**corridor-wide**, ±3 days — it was same-town until 2026-07-28, which is precisely why it missed the Doc Nancy duplicates: the submitter's town label and the resident row's disagreed, so the model was handed an empty candidate list and correctly concluded `publish_new` from it; candidates are now ranked exact-key → strong-match → same-town before a 40-row cap, and the prompt tells the model to treat town as a soft label on both sides), then web-searches (Anthropic `web_search_20250305` + Sonnet `claude-sonnet-4-6`) for the organizer/canonical page, and stores a verdict on the row (`ai_verdict` ∈ `publish_new | duplicate | duplicate_needs_update | reject`, plus `ai_confidence`, `ai_headline`, `ai_matched_event_id`, and a full `ai_analysis` jsonb of rationale / new_info / suggested-field-fills / sources / flags — migration `20260606_submission_triage.sql`). `/admin/submissions` renders a color-coded verdict banner, pre-fills blank publish-form fields from the research, and for `duplicate_needs_update` offers a one-click **Merge** (`mergeSubmission` in `actions.ts`) that fills only blank fields on the matched event (respects `*_locked`), snapshotting the prior row to `event_submissions.merge_snapshot` for reversibility. Triggered three ways: on submit via `after()` in `/api/submit-event`, a daily cron backstop (`/api/agent/triage-submissions`, 18:30 UTC), and a manual "Re-analyze" button. **The agent only advises; a human always clicks Publish/Merge/Dismiss.** The chief-of-staff digest reads these verdicts into `/admin/today`. **Reply loop (CRM):** each decision drafts a short reply to the submitter in the site's neighbor voice (`lib/agent/submission-reply.ts`, stored in `event_submissions.ai_reply`, migration `20260606b_submission_reply.sql`): **approve** → "your event is live" with the link; **"Draft a question"** button → asks only about the exact gaps the triage found; **dismiss with a reason** → a gracious decline (skipped for `possible_spam`). The admin UI shows the draft in an **editable panel** (`components/admin/EditableReplyPanel.tsx`, a client component) — Rob can tweak the subject/body in place and the one-click **Gmail compose deep-link** rebuilds live from the edited text (so the edits land in the pre-filled compose window); "Reset to draft" restores the agent's copy, and edits are page-local (not persisted to `ai_reply`). The app never sends mail; Rob edits and sends from his own Gmail (no inbox credentials in the app).
- **Email-to-event ingestion** (`PRD-email-ingest.md`) — a **thin front door** on the triage engine above. A curator forwards an event email (often with a poster) to a Resend Inbound address → [`/api/inbound-email`](app/api/inbound-email/route.ts) (Svix-signed webhook + sender allowlist `INBOUND_EMAIL_ALLOWLIST`, fails closed). Resend's `email.received` webhook is metadata-only, so the route fetches the body + attachments back (`resend.emails.receiving.get` / `.attachments.list`), reads the email **and** the poster via Sonnet, uploads the flyer to the `event-posters` bucket, and lands a `source='email'` pending `event_submissions` row — then fires the **same `triageSubmissionById`** the form uses. Everything downstream is reused unchanged: the triage verdict, the `/admin/submissions` review (now with an "Email" badge + "Original email" view), the reversible `mergeSubmission`, and publish-pins-the-poster. Idempotent on Resend's `email_id`. Pure core (prompt/parse/normalize/signature) in `lib/inbound-email.ts`, locked by `scripts/test/inbound-email.test.ts`. Columns added: `source`, `poster_url`, `raw_email`, `source_message_id` (migration `20260604b_email_submissions.sql`).
- Weekly recurring events use `is_weekly: true` and get collapsed in the UI (`CollapsedEvent` type)
- **Homepage feed collapse + Highlights toggle ([lib/collapse-events.ts](lib/collapse-events.ts), 2026-07-08).** The 60-day homepage window carried ~530 rows of which ~2/3 were instances of ~30 recurring series (Big Trees guided walks 40×, Junior Rangers 35×, weekly storytimes/trivia/maker sessions) wallpapering the same card onto every day-group — the clutter problem. `collapseEventList` (pure, locked by `scripts/test/collapse-events.test.ts`) says each happening once: **runs** (span ≤7 days, or a near-daily median cadence over a longer span — festival nightly rows, weekday camps) become one date-range card (`endDate`/`dayCount`; the old EventList multi-day behavior, preserved), and **spaced weekly-ish series** become their next not-yet-ended occurrence with a data-derived `seriesCadence` chip ("Weekly"/"Repeats") + `seriesCount`. ## Deduplication (defense in depth)

The same real-world event can appear twice: one source re-lists it under a changed title, or two sources describe it independently (e.g. the GoCalaveras aggregator lists "Live Music @ The Lube Room" while the venue feed lists "Live at The Lube: Poison Oakies" — same night). The title-based `dedup_key` only catches byte-identical re-scrapes of the *same* title, so it cannot see these. Four layers guard against dupes:

1. **Read-time assertion (downgraded from a collapse 2026-08-11, HWY-16)** — [lib/dedupe-events.ts](lib/dedupe-events.ts) used to run `dedupeEvents` on every user-facing list (homepage, town pages) and both briefing generators, silently merging any cluster it found into one card. It now runs the loud, non-collapsing `assertNoResidentDuplicates` at those same call sites (`lib/events-data.ts`, `app/api/generate-briefing`, `app/api/generate-weekend-briefing`) instead: identical clustering underneath (`findDuplicateClusters`/`clusterEvents`, keyed only on `date | visibility` — town and start were both dropped from the bucket key by fixes documented below, since either one being present let a real duplicate hide from the predicate entirely) and the same strong-identity-signal bar (near-identical title, overlapping artists, near-identical description, or same venue + a generic/umbrella placeholder title; two different specific titles never merge on venue/time alone), but instead of keeping the *enriched* survivor (`mergeCluster`) and dropping the rest, a found cluster now just gets one greppable `console.error` (prefix `READTIME_DEDUPE_ASSERT`, naming the date, venue(s), and every member's name + id) and **every row is returned unchanged**. **Why:** `/api/reconcile-dupes` (layer 3) has run live since 2026-07-01, and `/api/check-events` held 0 same-event duplicate clusters for 4 consecutive weeks — the canary the Open item below was gated on. The write-time merge and the nightly reconcile now own dedup at rest; this layer's job is to make a regression loud, not to keep silently mopping one up. `dedupeEvents`/`mergeCluster`/`clusterEvents`/`findDuplicateClusters` themselves are unchanged and still power `lib/reconcile.ts` and the `/api/check-events` audit.
2. **Write-time merge** — `scripts/lib/dedup.ts` (`isStrongEventMatch` / `buildStrongMatchUpdate`) replaces the old name-only fuzzy. When a scraped event has no `dedup_key`/`source_event_id` hit, it merges into an existing same-date/same-town row that shares an exact time slot + the same strong signal, field-merging so the survivor keeps the best of both (and unions artists). Conservative — never merges on title similarity alone.
3. **Continuous reconcile (self-healing identity)** — [lib/reconcile.ts](lib/reconcile.ts) (`reconcileDuplicates`) operates on DB state, blind to who wrote the rows, so it covers **every** write path — the `upsertEvents` scrapers AND the three raw-insert writers (`scrape-bls`, `scrape-moose-lodge`, `bistro-espresso`) AND any future writer. It clusters resident rows with the same shared `clusterEvents`/`pickSurvivor`, back-fills the survivor from its losers, and deletes the losers — writing a full reversible snapshot to `event_merge_log` **before** each delete. Run daily by [`/api/reconcile-dupes`](app/api/reconcile-dupes/route.ts) (15:30 UTC, after scrapes, before the audit). **Live since 2026-07-01** (`RECONCILE_EXECUTE=true` in Vercel production; it ran report-only from 2026-06-09 to 06-30 plus 14 manual one-off merges). Unset the env to fall back to dry-run; `?execute=1` forces a one-off. Every merge is reversible: `INSERT INTO hwy4_events SELECT (jsonb_populate_record(null::hwy4_events, merged_snapshot)).* FROM event_merge_log WHERE merged_from_id = '…'`. **Merged-away URLs don't 404:** the detail page's stale-slug recovery (`findEventFallback` in [lib/events.ts](lib/events.ts)) consults `event_merge_log` *ahead of* the fuzzy name matcher — it recomputes each same-date snapshot's slug for an exact loser-slug → survivor mapping (following a short survivor-was-later-merged chain; service-role read since the table is RLS-locked, degrades to a plain 404 without the key), so a shared/indexed link to a reconciled loser 301s to the survivor instead of dying. Locked by the `matchMergedSlug` cases in `scripts/test/events-fallback.test.ts`.
4. **Backfill + audit** — [scripts/backfill-dedup.ts](scripts/backfill-dedup.ts) is a thin CLI wrapper over the same `reconcileDuplicates` engine: `tsx backfill-dedup.ts` (dry-run) / `--execute` (apply). Needs `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`. `/api/check-events` reports same-event dupes (venue+time, different title) that the old name-only check missed, plus a `merges_last_24h` count.

The "same event" rule is defined **once** in `lib/event-identity.ts` (`isSameEvent`, locked by `scripts/test/event-identity.test.ts`) and reused everywhere via `lib/dedupe-events.ts` (`clusterEvents`/`pickSurvivor`): the read-time assertion, the write-time merge (`scripts/lib/dedup.ts`), the reconcile engine, the backfill, and the audit all import it, so the definition can't drift.

**End-time forgiveness + locality-venue strip (2026-07-05, the Coffee & Cars triple):** three sources listed the same Meadowmont Lodge car show with three different extracted end times (11:00 / 17:00 / 12:00 — Visit Murphys' own description said "8am to 11am" while its structured end said 5pm), and the old ends-must-agree-when-both-known rule was a hard veto, so every dedup layer was blind to the triple for six weeks. Now `timesAnchor` forgives a conflicting known end **when the venues agree** (name fuzzy or street-number anchor): same venue + same date + same start is one physical slot, so a differing end is scrape noise. When the venues *don't* provably agree (one side unknown), conflicting ends still split the rows. Separately, `venueForMatch` strips a Facebook-style trailing locality (`"Meadowmont, California"` → `meadowmont`, comma required) so the place core can fuzzy-match the real venue (`Meadowmont Lodge`) instead of tripping the different-venues veto; when the remainder is just the event's own town (`"Arnold, California"`), the venue is treated as unknown (mergeable on title/artists/description, but never able to anchor a venue-based signal). Both locked in `scripts/test/event-identity.test.ts`; a full-catalog dry-run at ship time confirmed the triple was the only cluster the loosening added.

**Town is a label, not an identity key (2026-07-28, the Doc Nancy dupes).** A community submission put Calaveras Big Trees State Park in **Camp Connell**; the park's own listing says **Arnold** (its mailing address). Same program, same night, same 8:00 PM start, two cards on the homepage. Town was a hard veto at the top of `isSameEvent` **and** a component of the read-time bucket key, so the read-time collapse, the write-time merge, the nightly reconcile, and the triage agent's candidate query were **all** blind to it at once. The corridor is one continuous string of settlements along Highway 4 and several venues sit near a boundary, so the town label is a human guess on *both* sides of the comparison. Four changes: (1) the town veto now fires **only when the venues do not provably agree** — a shared `venue_key`, a venue-name match, or a street-number anchor outranks a differing label, and the usual identity signal is still required on top; (2) `venue_key` joined `EventIdentity` as the strongest venue signal (registry-resolved, immune to spelling), and `venueTokensAgree` fuzzy-matches a venue rewritten from both ends at once ("Calaveras Big Trees State Park" vs "Big tree State Park overlook") at a deliberately high bar (≥3 shared distinctive tokens AND ≥80% of the smaller name, which still rejects "Bear Valley Lodge" vs "Bear Valley Adventure Company"); (3) `bucketKey` in `lib/dedupe-events.ts` **dropped town** — it was the last silent second copy of a rule that lives in the predicate, the same failure shape as the `start_time` component HWY-10 removed, and no loosening inside `isSameEvent` could be reached through it; (4) `titlesShareTokens` discounts venue words when the venues agree, as a **second chance only** (never a replacement — venue words shared by both titles are shared tokens, and removing them can only lower Jaccard, so a strip-instead-of-add would silently un-merge existing matches). That last one caught a **second** duplicate from the same submitter the same week ("Optical astronomy big tree State Park" vs "Optical Astronomy Nights @ Big Trees State Park"), where one source separates the venue with "@" and the other runs it into the title. Full-catalog dry-run at ship time: over the entire upcoming set, exactly 6 pairs clear a superset of the matcher's gates, all 6 genuine duplicates, and the only **new** merges are the 2 community dupes. Both were merged reversibly via `event_merge_log`. Locked by `scripts/test/event-identity.test.ts` + `dedupe-events.test.ts`.

**An identical start-AND-end window is its own identity signal (2026-08-11, the Rotary shrimp feed).** Two aggregators listed the Angels-Murphys Rotary shrimp feed at Murphys Community Park on Aug 15, both 16:00–21:00, both resolved to `venue_key='murphys-community-park'` — and every text signal missed by roughly half: titles 0.33 against the 0.85 bar ("Rotary's Annual Shrimp Feed & Auction" vs "Annual Shrimp & Pasta Feed Fundraiser"), descriptions 0.27 against 0.92, description token overlap 0.25 against 0.70, title tokens 0.375 against 0.60, both `artists` arrays NULL. Each source wrote its own title *and* its own prose, so there was no shared string structure to grab. Because all four layers reach the one predicate, the pair was simultaneously invisible to the read-time collapse, the write-time merge, the nightly reconcile **and** `/api/check-events` (which reported `same_event_duplicates: 0` while both cards sat on the homepage — `findDuplicateClusters` is just `clusterEvents(...).filter(c => c.length > 1)`, so the audit is not an independent check for this class, and the one predicate-free check, `timeless_near_dupes`, only fires when a NULL-start row is involved). `sameExactWindow` adds the last-resort signal: same venue + start AND end both known on both sides and both equal. **The end time is what makes it safe, and it is not a detail** — measured over the whole upcoming catalog, same-venue + same-date + same-**start** yields 6 pairs of which only 1 is a duplicate; the other 5 are Calaveras Big Trees genuinely running Junior Rangers, Meadow Walk and the South Grove Guided Hike all at 10:00 in the same park, so merging on the start alone would have silently deleted four real programs. Requiring both ends known and equal leaves exactly the 1 true duplicate (the park's programs are different lengths). A NULL end on either side never matches — treating NULL as equal re-admits the Big Trees pairs. **Naming different acts disqualifies the window outright**: a venue can run a Salsa Night with Los Caminos and an Open Mic with Jane Doe in the same 19:00–21:00 slot, and two rows that each name an act and disagree on who is playing are asserting two different shows, which outranks the matching clock. Ship-time dry run: 25 upcoming pairs share an exact window, 24 die at the different-venues veto (no street-number coincidences), and the 1 that reaches the new signal is the shrimp feed. Merged reversibly via `event_merge_log`. Locked by `scripts/test/event-identity.test.ts`.

**Match-time normalization + address anchor (2026-07-04, the Arts & Crafts Festival dupe):** title/description similarity compares via `normalizeForMatch` — `normalizeName` plus "&"→"and" folding and a leading "Nth Annual"/"Annual" strip — so "54th Annual Sierra Nevada Arts & Crafts Festival" matches "Sierra Nevada Arts and Crafts Festival". This is deliberately NOT applied in `generateDedupKey`: changing that hash would orphan every stored dedup_key and re-duplicate the catalog on the next scrape (key stability is test-locked). Separately, the different-venues veto is softened by a **same-street-number address anchor** (`sameStreetNumber`): two sources naming the same lot differently ("Bristol's Ranch House Cafe" vs "Bristols's Cafe Parking Lot", both at 961 Highway 4) no longer trip the veto. The anchor needs a ≥2-digit street number on both rows and never merges on its own — one of the usual identity signals (title / artists / description / generic-title / act-named) is still required.

> **Open item (dedup Move 3, Step 4):** Step 1 (assertion) shipped **2026-08-11 via HWY-16** — the canary held (four consecutive weeks of `/api/check-events` reporting 0 same-event clusters + 0 surprising merges, clock started 2026-07-01 when `RECONCILE_EXECUTE=true` went live in Vercel prod), so read-time `dedupeEvents` was downgraded from a collapse to the loud `assertNoResidentDuplicates` at every user-facing call site (see layer 1 above): it still detects a cluster with the identical clustering logic, but now only logs `READTIME_DEDUPE_ASSERT` and passes every row through untouched instead of merging. **Remaining step:** after a clean soak under the assertion (watch server/Vercel logs for `READTIME_DEDUPE_ASSERT` — silence means the write-time merge + nightly reconcile are holding at rest with no read-time backstop needed), remove the assertion from those call sites entirely a release later. `dedupeEvents`/`clusterEvents`/`pickSurvivor`/`findDuplicateClusters` themselves stay put either way — `lib/reconcile.ts` and `/api/check-events` still depend on them.

## Manually Curated Venues

Some venues publish their schedule in a form the scrapers can't read — e.g. The Lube Room Saloon posts its "Live at the Lube" lineup only as an image, the Camp Connell General Store posts its "Beer Garden" concert lineup only as a season poster, and Calaveras Big Trees State Park posts its season as recurrence rules in prose ("Creek Critters: June 13 – August 15, Tuesdays and Saturdays"), which aggregators re-list as wrong, flattened rows. A weekly recurring event can also arrive by **community submission** with no readable source at all — e.g. the Arnold Library's "Storytime with Miss Debbie" (Wednesdays 10:30 AM); the county library publishes no calendar the scrapers can reach, so it's owned by a seed script too. These are curated by hand and protected two ways:

- **A seed script owns the rows** (e.g. `scripts/seed-lube-room-summer-2026.ts`; `scripts/seed-camp-connell-beer-garden-2026.ts`; `scripts/seed-arnold-library-storytime-2026.ts` (weekly Wednesdays, expanded via `recurrence.ts`); or `scripts/seed-bigtrees-programs-2026.ts`, whose schedule rules live in `scripts/lib/bigtrees-schedule.ts` and expand to dated rows via the tested `scripts/lib/recurrence.ts`). Edit the data there and re-run to change a venue's events.
- **`scripts/lib/manual-sources.ts`** (`isManuallyManagedEvent`) lists venue/name substrings; every auto-scraper skips matches before upserting, so a re-scrape can't overwrite the hand-entered rows. Cameo Plaza, The Lube Room, Calaveras Big Trees State Park, the Camp Connell General Store (incl. its "Beer Garden"), the Arnold Library, the Murphys Senior Center, and Lake Alpine Lodge are blocklisted today. The Lake Alpine pattern is deliberately `"lake alpine lodge"`, not the bare `"lake alpine"`: BVAC's events page has real non-lodge events at the lake (e.g. "Lake Alpine Kid's Fishing Day") that the broader substring would silently drop, and every seeded lodge row carries venue_name "Lake Alpine Lodge" so the narrow pattern still protects them all. Also blocklisted by **event name** (not venue): the **Hot Copper Car Show** (Copperopolis Town Square) — a hand-curated Rob's Pick / America's-250th feature whose GoCalaveras listing carries a doubled title ("Hot Copper Car Show Show", slug `hot-copper-car-show-show`) and a 23:50 placeholder end time; freezing the row keeps the hand-corrected name + 8 AM–3 PM time from reverting on the daily scrape, while the other event at the same square (July 4 "Stars & Stripes") still scrapes normally.
- **The blocklist is ownership-aware (2026-07-25).** Each entry is `{ pattern, owner? }`, and `isManuallyManagedEvent(event, askingOrgSlug?)` blocks a match only when `owner !== askingOrgSlug`. An entry with **no** `owner` is owned by a seed script / human, so *every* scraper is blocked (the original behavior, unchanged for all existing entries). An entry **with** an `owner` is owned by a scraper that reads that organizer's own calendar: the aggregators (which call the predicate with no slug) stay blocked, while the owning source passes its slug and writes freely. First user: `arnold-rim-trail` owns `arnold rim trail` / `aronld rim trail` (the source's real typo) / `cougar rock` / `volunteer trail workday` / `art trailhead`, so GoCalaveras can't overwrite the organizer's sunset-hike times with its stale snapshot on a later pass of the same nightly run. **Gotcha:** call it as `.filter((e) => isManuallyManagedEvent(e))`, never `.filter(isManuallyManagedEvent)` — the bare reference passes the array index as `askingOrgSlug`. Locked by `scripts/test/manual-sources.test.ts`.

- **A seed script does NOT imply a blocklist entry (2026-08-14, Hinterhaus Distilling).** `scripts/seed-hinterhaus-tours-2026.ts` hand-enters the distillery's distiller-led tour Saturdays (announced only on their Facebook page + the VISIT page of hinterhausdistilling.com), and the venue is deliberately **not** in `manual-sources.ts`. The blocklist exists to stop an aggregator that is *actively* re-listing a venue's events over curated rows; Hinterhaus had **zero** `hwy4_events` rows from any source before the seed, so an entry would buy no protection today and would silently drop the first real listing whenever a scraper does pick the venue up. The hand-entered specifics are protected per row instead (`description_locked` + `times_locked`). Blocklist it if a scraper ever starts overwriting these rows.

For schedules the scrapers can't read, a watcher cron fingerprints the source and pings Slack on change without auto-writing: `/api/check-lube-schedule` (the Lube Room's image), `/api/check-bigtrees-schedule` (Big Trees' program text on parks.ca.gov), `/api/check-camp-connell-schedule` (the Camp Connell General Store's Squarespace poster), and `/api/check-murphys-senior-center-schedule` (the Murphys Senior Center's monthly calendar images on murphyscenter.com).

### Festival "umbrella" rows (intentional duplicates — do NOT merge)

A multi-week festival reads as ~13 look-alike daily cards with no single "this is a festival, here are the dates" entry (the schema is single-date — no `end_date`). The fix is a **purposefully duplicative umbrella row**: one curated event dated the festival's opening day with a NULL `start_time` and a year-suffixed title, alongside the real nightly shows. It carries `robs_pick=true` so it rides the homepage from now through opening day. **If you see two same-day festival cards (e.g. "Bear Valley Music Festival 2026" + "Bear Valley Music Festival" on Jul 17), that is by design — not a dedup bug.**

**`series_umbrella` is what keeps it separate (2026-07-27, HWY-10).** Originally the separation was a side effect of the NULL `start_time`: `timesAnchor` required two known, equal starts, and the read-time bucket keyed on `town|date|start|visibility`, so a timeless row could never even be compared to a timed one. That protected the umbrella and, unavoidably, **every real duplicate that merely omitted a start time** — invisible to the read-time collapse, the write-time merge, and `/api/reconcile-dupes` alike (the Kane Brown Ironstone double, merged by hand 2026-07-16; the Moose Lodge triple; a live "Rib Feed & Live Band" pair). Now the marker is explicit: `hwy4_events.series_umbrella` (migration `20260727_series_umbrella.sql`, default false) is set **only by the seed scripts** — every scraper writes false — and `isSameEvent` skips the timeless path when either row carries it. With umbrellas protected by intent, a row that states no start anchors on the **venue** instead of the clock (`venuesAgree` required, plus the usual identity signal), so a timeless duplicate merges normally. The bucket key dropped `start` at the same time, so it is a pure performance pre-filter again rather than a silent second copy of the time rule. Survivor selection prefers a row that states a time, and both `mergeCluster` and reconcile's `buildFill` back-fill the clock onto a timeless survivor, so a merged card never loses the hour. Locked by `scripts/test/event-identity.test.ts` (the umbrella non-merge is asserted explicitly, including that dropping the flag makes the same pair mergeable), `dedupe-events.test.ts`, and `audit-checks.test.ts`. Live dry-run at ship time: 4 clusters over the 90 affected rows, all genuine.

- **Bear Valley Music Festival** (Jul 17 – Aug 2, 2026): the umbrella + a band-name backfill for the nightly shows are owned by `scripts/seed-bear-valley-music-festival-2026.ts` (idempotent; `--dry-run` to preview, `--cleanup-capstone` to also delete the older "(through Aug 2)" row). The nightly rows stay **scraped** (GoCalaveras) and are deliberately **not** blocklisted in `manual-sources.ts` — instead of renaming them (which would churn their title-based `dedup_key`), the script fills each night's act into `artists` (rendered as a card chip), guarded on `artists IS NULL` so re-runs and re-scrapes (which union artists) preserve it. To refresh for next year, edit the lineup/dates in that script and re-run. The Big White Tent is venue_key `big-white-tent`; the umbrella links durably to `bearvalleymusicfestival.org/2026-festival`.

## Event Notability (hide routine venue operations)

Some venues publish their own restaurant/lodge calendar, so their day-to-day operations leak in as fake "events": Sequoia Woods Country Club lists a weekly **"Thursday Night Dinner"** and **"Wednesday Night Deli Special"**; the Moose Lodge lists recurring dinners/breakfasts and "open for [holiday]" meals. Being open to serve a meal is not an event; a special occasion with a hook (live music, a guest, a theme, a one-off) is. A `is_routine` flag hides the former from every public surface while keeping the latter.

- **The judgment lives once in [lib/notability.ts](lib/notability.ts)** (`classifyNotabilityDetailed` + `reconcileNotability`), structured exactly like `lib/categorize.ts`: a **Tier-0 notable hook** (`category==='live_music'`, or tokens like car show / karaoke / featuring / trivia / fundraiser / scramble / crab feed) that **beats** the routine floor — so "Special Monthly Dinner **with Live Music**" stays — then a **Tier-1 authoritative routine** floor (`<weekday> [night] <meal>`, deli/daily specials, named nights, "open/serving for <holiday>", holiday-meal, and title-leading "Private <party/event/rental>" hall rentals, added 2026-07-17) that an LLM cannot lift, then a **Tier-2 soft** tier (bare `brunch`/`buffet`, or `is_weekly` + a meal noun) the LLM may confirm or clear. **Bare `dinner`/`lunch` is deliberately NOT soft-routine** — real events say "…/ Dinner" (e.g. the "Sequoians Summer Scramble SG / Dinner" golf event stays). Locked by [scripts/test/notability.test.ts](scripts/test/notability.test.ts).
- **Columns on `hwy4_events`:** `is_routine` (the hide flag), `notability_locked` (human override — when true no writer touches it, mirrors `price_locked`/`description_locked`/`poster_locked`), `routine_reason` (which rule / `"llm"` fired, audit only). Migration `20260701c_add_notability.sql`.
- **Blast-radius invariant — ONLY `sequoia-woods` + `moose-lodge` ever set `is_routine=true`.** The floor runs inside the shared `upsertEvents` (`scripts/lib/dedup.ts`, `OPERATIONAL_ORG_SLUGS` gate) so Sequoia + the Moose public-events page are covered with no per-scraper edit; the self-contained Moose PDF route (`app/api/scrape-moose-lodge/route.ts`) does its own floor + an `is_routine` LLM field, reconciled by the floor. Every other source writes `false`. **Do NOT wire the flag into any other scraper** — the read filter is global and trusts that only these two venues populate it. Self-heals + is reversible per row like the other locks (`UPDATE … SET is_routine=false, notability_locked=true WHERE id=…`).
- **Read-time hide:** `.neq('is_routine', true)` on the shared `getUpcomingEvents` fetch ([lib/events-data.ts](lib/events-data.ts)) covers the homepage, town pages, temporal pages, and sitemap; the by-slug/fallback lookups ([lib/events.ts](lib/events.ts)) add it too, so a hidden event's detail page **404s** (consistent with cancelled) and never appears in the sitemap. The three standalone queries that bypass the shared fetch also filter it: `app/api/generate-briefing`, `app/api/generate-weekend-briefing`, and `lib/newsletter.ts`. It is filtered in SQL, so `is_routine` never crosses the wire (not in `EventListItem`).
- **Backfill existing rows:** `cd scripts && npx tsx backfill-notability.ts` (dry-run) / `--commit` (apply) — scoped to the two orgs, skips `notability_locked`, floor-only (no LLM). One-time; new scrapes self-heal via the write path.

## Weekly PM pass (a scheduled task, NOT a Vercel cron)

The cockpit had five proposers and no closer. Measured 2026-07-29: 11 growth memos had produced 7 tickets (5 shipped), the board was drained to **0** open tickets, three `growth_experiments` had been `running` for 33 to 52 days, and `growth_lessons` held **0** rows. `lib/agent/growth-lessons.ts` (HWY-5) only distills a lesson from a *concluded* experiment, so the growth agent's memory loop had never once fired and every Friday memo reasoned from scratch.

**[.claude/skills/pm-review/SKILL.md](.claude/skills/pm-review/SKILL.md)** is the closer. It concludes experiments that are past a 28-day eligibility floor: translate the prose `metric` field into aggregate SQL, compare the window since `started_on` against an equal-length window before it, and write `status` + `result` + `concluded_on`. The next Friday memo then captures those into `growth_lessons` via the existing `captureLessonsFromConcludedExperiments` and reads them back in the same run, so **nothing new writes lessons** and the loop closes in ~24h.

**It runs as a Cowork scheduled task** (`~/.claude/scheduled-tasks/hwy4-pm-weekly/`, Thursdays ~8:30am PT, ahead of the Friday memo), not a Vercel route, because rendering an honest verdict needs a repo and a shell: the metric is prose that has to become SQL, and `git log` over the window is how you catch a confounder. The cron reasoners have neither. Same shape as `hwy4-persona-qa-daily`: the task file only pulls the repo and delegates, and the *spec* is the repo-committed skill, versioned alongside the code it reasons about.

Writes an `agent_runs` row with `run_type='pm_review'`. **Verdict bias is deliberate: default to `inconclusive`.** Weekly volumes here are small, and a lesson gets injected into later prompts as ground truth, so a flattering `won` poisons every future memo. Same never-guess contract as the price extractor and the artist-blurb drafter. It may never write `abandoned` (killing an experiment is Rob's call), never touch `hwy4_events`, never publish, never push code. Every conclusion reverts with one `update`. PRD-ifying tickets and ranking the board are later phases, explicitly out of scope.

**First run (2026-07-30) concluded all three stale experiments `inconclusive`, and none for a boring reason:** the live-music venue-section test was confounded (clicks per event-detail session fell 0.0344 → 0.0160 while sessions grew 4.5x once Google organic started Jun 19, mid-baseline, so the ratio measures audience mix; its secondary metric was met at 209/214); the after-event-5 signup box had no valid baseline (all 79 prior rows predate source tagging) and the real finding was comparative, `event_detail` placement out-producing `homepage_event5` in half the time; and the host kit was never distributed (**zero** `src=host` events ever, `/hosts` drew 5 views and none since Jun 18), so it is untested rather than failed. Two experiments declared metrics their own instrumentation could not measure at their start, which is the process lesson: **an experiment needs a horizon and a baseline snapshot at creation time.**

Migration `20260729_agent_runs_pm_review.sql` shipped with it and fixes **two latent bugs found while wiring this up**, both of which had silently disabled a documented feature:

1. **`agent_runs_run_type_check` only allowed `chief_of_staff|growth_memo`.** `/api/agent/scraper-health-memo` has inserted `run_type='scraper_health'` since it shipped, so every Monday it burned a Sonnet call, had its insert rejected, failed its error-path insert the same way, and 500'd. `/admin/scrapers` (the Pulse "Scrapers" tab) had therefore never rendered a memo. Zero `scraper_health` rows existed as proof.
2. **`growth_lessons_experiment_uq` was a PARTIAL unique index** (`WHERE source='experiment' AND source_ref IS NOT NULL`) while the capture upserts with `onConflict: "source_ref"`. This is the identical gotcha already documented for `seo_snapshots`: **PostgREST `onConflict` cannot name a partial index.** Postgres raised 42P10, the capture caught it and returned 0, so the memory loop could not have written a lesson even once an experiment was concluded. Concluding experiments alone does not close the loop. Replaced with a plain unique index (NULLs are distinct, so manual lessons are unaffected); verified with a rolled-back `on conflict (source_ref)` probe against prod, failing before and inserting after.

## Newsletter email rendering ([lib/newsletter.ts](lib/newsletter.ts))

`buildEmailHtml(robNote, content, unsubscribeUrl)` is the single source of truth for the email HTML — both the Thursday send and the `?preview=1` route use it, so what you preview is what ships. Body + "From Rob" note are markdown-ish (`[label](url)` links) wrapped into `<p>` by `renderParagraphs`, which **normalizes CRLF→LF first** (admin-textarea edits arrive as `\r\n\r\n`, which a naive `split("\n\n")` misses and collapses into one block).

- **Layout:** 640px shell, 18px body / line-height 1.6, forest-green hero (`#1B3A2D`) with the site's Big Trees sequoias flanking the title + Millie peeking onto the cream below. Tuned against pro newsletters (Feed Me, Walk With History) — wider + larger type than the old 560/16.
- **Scannable spine:** `boldEventAnchors` bolds **dated** weekday anchors ("Friday, June 5", "Saturday the 6th") and the "Rob's Pick" lead-in (body only, not the From-Rob note). Render-time + deterministic, so it lands on every draft — including already-queued/edited ones — with no dependency on the model emitting markup. Bare day names are deliberately left unbolded.
- **Voice:** the generation prompt (`NEWSLETTER_SYSTEM_PROMPT`) treats the email as a **teaser, not the full calendar** — be selective, the site carries the complete lineup, the email earns the click.
- **Brand assets:** email clients don't render SVG, so the hero marks are PNGs in `public/email/` (`tree.png`, `millie-happy.png`), served from `SITE_URL` at send time. Regenerate from the site's SVGs with `node scripts/generate-email-assets.mjs`.
- **Scanner-safe funnel (2026-07-03):** `/api/newsletter/confirm` and `/api/newsletter/unsubscribe` render a read-only interstitial on GET and perform the action only on POST — mail-security scanners prefetch every GET in an email, and the old GET side effects let a scanner fake a confirm or silently unsubscribe a real reader on every Thursday send (a confirm-rate/subscriber leak). The unsubscribe POST doubles as **RFC 8058 one-click** (every send now carries `List-Unsubscribe` + `List-Unsubscribe-Post`, the Gmail/Yahoo bulk-sender requirement). First confirm sends a one-time **welcome email** (`buildWelcomeEmailHtml` in [lib/newsletter.ts](lib/newsletter.ts), best-effort so it never blocks the confirm; copy locked by `scripts/test/newsletter-welcome.test.ts`).

Most events come from the `scripts/scrape.ts` orchestrator, run daily by
`.github/workflows/scrape.yml` (a GitHub Action, **not** a Vercel cron). It
dispatches per-source scrapers and writes through the shared
`scripts/lib/dedup.ts::upsertEvents` path (dedup_key + corridor drop +
cross-source merge). Two source shapes:

- **Config-driven Firecrawl** — one entry in `scripts/scrapers/firecrawl-sources.ts`
  (single fixed venue/town). The generic runner fetches markdown + LLM-extracts.
  **Registry audited + trimmed 2026-08-11 (HWY-20):** `watering-hole` +
  `branding-iron` deleted (zero rows ever — neither site has an events page;
  gocalaveras covers The Watering Hole accurately) and `lube-room` +
  `camp-connell-general-store` deleted (silently zero for 65+ days, 100%
  unpinned, writing under the identical org_slug/source_name as their seed
  scripts — an invented row would have been indistinguishable from a curated
  one; the seeds + fingerprint watchers own those venues). Three entries
  remain: `bear-valley` (now with a commerce-promo `extractHint` + `dumpOnEmpty`),
  `bvac`, and the `moose-lodge` public-events page (its 3 marquee public rows
  are disjoint from the members' PDF calendar — unique coverage, kept).
  A source may set `extractHint` — a per-source instruction appended to the shared
  extraction prompt's Rules (added 2026-07-08 for **bvac**, Bear Valley Adventure Co.:
  skip its season-pass-sale promos, lift each event's own venue + Squarespace
  permalink; see `PRD-bvac-events.md`). The shared extractor also skips already-past
  events by prompt (BVAC's page lists past events alongside upcoming; the runner's
  date filter stays as the backstop) and runs at `max_tokens: 8192` — a ~50-event
  page overflows 2048 and truncated JSON silently extracts 0.
- **Special scrapers** — hand-written files for non-generic shapes (GoCalaveras
  EventON AJAX, visit-murphys + arnold-rim-trail WP REST, **red-cross**, …),
  registered in `SPECIAL_SCRAPERS`. **Organizer-owned sources are listed first**
  in that object so a same-night aggregator pass is never the last writer on a
  row they own (the `manual-sources.ts` blocklist is the real guard; ordering is
  belt-and-braces).

**Organizer-source skeleton ([scripts/lib/organizer-source.ts](scripts/lib/organizer-source.ts), HWY-23, 2026-08-11).** Four scrapers read an organizer's own structured feed — `brice-station` (Shopify products.json), `arnold-rim-trail` (Tribe REST), `sequoia-woods` (a Duda month grid), `murphys-irish-pub` (Wix per-event pages) — and had independently grown the same tail. That sequence is now declared once. `beginOrganizerRun({title, sourceName, orgSlug, pageUrl})` banners the run and reads the run date **once** (the future floor and any sweep window must compare against one string, not two clock reads either side of UTC midnight); `writeOrganizerBatch(run, {events, privateEvents?, planSweep?})` — the DB half in `organizer-source-exec.ts` — applies a future-only floor, upserts public-then-members-only (skipping an empty group; `upsertEvents` takes one visibility per call), then runs the source's sweep plan: **after** the write (sweeping first would archive-and-delete rows the upsert is about to refresh), under the **same `org_slug` the write used**, and **only when the run actually wrote rows** — an empty batch can't be told apart from a broken fetch, and a sweep with an empty presence set selects every resident row in its window. Deliberately **not** unified, because unifying them would change behavior or hide judgment: each source's fetch, its per-item mapping and logging, venue detection (three call it, each reporting differently), each bespoke summary block, and every sweep input that decides what gets deleted — the window derivation, the presence set, the ownership predicate — which stay in the scraper that can explain them. `brice-station` and `arnold-rim-trail` pass no plan at all (their file headers say why neither may retract). Pure rules locked by `scripts/test/organizer-source.test.ts`; the sweep primitive itself is unchanged (`stale-sweep.ts`, which now also defines the shared `SweepPlan` option shape).

**URL-stated date/time correction ([scripts/lib/url-date.ts](scripts/lib/url-date.ts), 2026-07-26).** Organizer permalinks routinely carry the occurrence date, and sometimes the start time, in a string the venue authored themselves (`bricestation.com/products/wolf-jett-july-25-2026-7pm`, `visitmurphys.com/event/music-on-the-rooftop/2026-07-31/`). That beats an LLM's reading of a rendered page. `correctFromUrl` runs in the shared `upsertEvents` pre-pass **before `dedup_key` is computed** (so the corrected date keys the row) and covers every scraper. **The Wolf Jett bug it closes:** the `brice-station` scraper wrote a row dated 2026-07-26 for an event whose own product URL said July 25 — the correct July 25 row already existed, so the site showed a duplicate advertising a show that had already happened. Deliberately a *correction, never a source*: it only overrides a date/time already extracted, only from the event's own `event_url`, and only when the URL states one unambiguously — a month **name** + day + 4-digit year, or an ISO path segment; a bare year ("…-2026"), a season, and "4th-of-july-2026" all parse to null, as does a calendar-impossible date. A slug time needs an explicit meridiem (a bare number is too ambiguous). Every correction is logged (`URL_DATE_CORRECTION`) — it firing means an extractor is getting dates wrong and that should be visible. Locked by `scripts/test/url-date.test.ts`.

**Recurring-series ingest horizon ([scripts/lib/ingest-horizon.ts](scripts/lib/ingest-horizon.ts), 2026-07-25).** The Events Calendar materializes a recurring event as a real post per occurrence, so Visit Murphys' feed offers weekly instances **two years out** — and we ingested all of them: 104 rows of "Live Music Upstairs" at Boyle MacDonald, every one asserting a 6:00 PM start, running to 2028-07-21. Across the catalog that was 82 upcoming rows past 12 months from just 4 series (~12% of the whole upcoming set). Wrong for two reasons: **accuracy** (nobody confirmed a bar's trivia start time in July 2028, yet the site stated it as fact — the same "asserted a time we don't know" failure as the stale sunset-hike times, arriving from the other direction) and **crawl budget** (`PRD-search-indexing.md` blames exactly this population for the sitewide "Discovered – currently not indexed"; the sitemap was trimmed then, but the rows were never capped — this is the upstream fix). `capSeriesHorizon` runs in the shared `upsertEvents` pre-pass next to `dropOutOfCorridor`, so it covers **every** scraper, and is deliberately narrow: an event is dropped only when it is BOTH beyond `SERIES_HORIZON_DAYS` (365) AND one of `MIN_SERIES_SIZE` (6) or more instances sharing a name + venue in the same batch. A far-future **one-off** — next year's festival announced early — has a tiny group and always survives. Drops are logged per series (a silent cap would read as "we covered everything"). Locked by `scripts/test/ingest-horizon.test.ts`. The 82 resident rows were archived + deleted 2026-07-25; every one is restorable from **`hwy4_events_horizon_archive`** (migration `20260725_events_horizon_archive.sql`, service-role only): `INSERT INTO hwy4_events SELECT (jsonb_populate_record(null::hwy4_events, snapshot)).* FROM hwy4_events_horizon_archive WHERE event_id = '…'`.

**Unpinned-row guard ([scripts/lib/unpinned-guard.ts](scripts/lib/unpinned-guard.ts), HWY-17, 2026-08-11).** A row carrying **neither `source_event_id` nor `event_url`** is unverifiable (nothing to re-read), uncorrectable (`correctFromUrl` has no URL to check the date against) and unretractable (a window-scoped stale sweep keys rows by sid/URL, so it can never select one) — precisely the shape of all 36 Murphys Irish Pub phantoms. `partitionUnpinned` runs in the shared `upsertEvents` pre-pass, right after `normalizeBatch` (so it judges the URL that will actually be stored: post-`correctFromUrl`, post the non-http(s) null-out), and every call reports `UpsertResult.unpinned`, summed into `scrape_runs.source_results` by `recordSourceResult` so the count is durable per source per run. **The policy is per-source because most unpinned rows are legitimate:** the seed scripts transcribe schedules that have no per-event page anywhere (`lib/bigtrees-schedule.ts` literally writes both fields null), so a blanket rule would delete hand-curated events. Three policies: **`allow`** = expected shape here, nothing dropped and the count reported as **0** (not an anomaly worth a number on an ops dashboard); **`warn`** = the default, nothing dropped but the count reported (`UNPINNED_ROWS <source> <n> (policy=warn)` in the scrape log); **`reject`** = refused at the write boundary, one `UNPINNED_REJECTED` line per row. Today `allow` is set at exactly two callers, both seeds (`seed-bigtrees-programs-2026`, `seed-lube-room-summer-2026`); every scraper is on the default `warn` and **nothing is on `reject`**. The flip of a text-scrape source warn→reject is a later, soak-gated change: **7 consecutive clean days of zero warns for that source** first, which proves its rows are reliably pinned before keyless ones start being refused. Locked by `scripts/test/unpinned-guard.test.ts` (which asserts the `allow` no-op as hard as the `reject` behavior).

**Runner timeout + health logging (2026-07-09).** The GitHub Action job runs at
`timeout-minutes: 20` (raised from 10 — the job was landing right at the old
cap, hitting a runner-timeout **kill** on most days, which GitHub Actions
reports as `cancelled`, not `failure`, so the workflow's own `if: failure()`
alerting never fired). Independent of the timeout headroom, every run now
writes a durable summary to **`scrape_runs`** via
[scripts/lib/scrape-run-log.ts](scripts/lib/scrape-run-log.ts) — instrumented
once at `upsertEvents` (`scripts/lib/dedup.ts`, the one choke point every
scraper writes through) and flushed **right after the scraper loop, before**
the slower URL-validation pass, so a future timeout kill during validation
can't erase scraper health visibility again. Read at **`/admin/scrapers`**
(the Pulse "Scrapers" tab) — see the Admin cockpit section above.

### Organizer retraction — window-scoped stale sweeps (`scripts/lib/stale-sweep.ts`, 2026-08-09)

An append-only ingest plus an organizer who **edits** their calendar equals permanent ghosts: Sequoia Woods renamed "Patio Party #4 … (TBD)" to "… - The Hit Men" and the TBD row lived on beside it (reconcile caught that one only because the titles overlapped; a same-night act swap strands a ghost **no dedup layer may merge**, since different named acts are different events — that rule protects real back-to-back events and stays). Dedup can't fix rows that aren't duplicates; they're listings the source no longer asserts. Both organizer-owned scrapers (**murphys-irish-pub**, **sequoia-woods**) therefore run a **window-scoped stale sweep** after upserting: a resident row this source owns, inside the dates the run provably covered, absent from the batch, is archived to `hwy4_events_removed_archive` (migration `20260809b_events_removed_archive.sql`) then deleted. Both wire it through the organizer-source skeleton above, which owns the after-the-write / same-org / only-if-rows-were-written ordering; each scraper still supplies its own window, presence set and ownership test. Guardrails (pure core `scripts/lib/stale-sweep.ts`, locked by `scripts/test/stale-sweep.test.ts`; executor `stale-sweep-exec.ts`): only cleanly-parsed windows are sweepable (a failed/thin month view or list fetch contributes no window — and for the pub, every *linked* page counts as present even when unparseable, so a parse failure can never delete a row); rows carrying another source's sid/URL are untouchable; `robs_pick` / `community_sourced` / `series_umbrella` / any `*_locked` row is skipped and logged; selections above the effective cap abort the whole sweep as a bad fetch (`effectiveSweepCap`: the relative `maxSweepAllowed` — ~⅓ of resident rows, floor 3, ceiling 20 — further lower-bounded by an optional per-source `maxPerRun` budget); and **sweeps run report-only until `SWEEP_EXECUTE` names the source** (a GitHub Actions repository variable, not Vercel; an allowlist with no all-sources value — see Environment Variables). **First dry-run logs land 2026-08-11**: the last scrape before this shipped (Aug 10) predates the merge, so no sweep of any kind has yet run in prod. Restore any removal: `INSERT INTO hwy4_events SELECT (jsonb_populate_record(null::hwy4_events, snapshot)).* FROM hwy4_events_removed_archive WHERE event_id = '…'`.

**Aggregator retraction — the GoCalaveras sweep (`scripts/lib/gocalaveras-sweep.ts`, 2026-08-11, HWY-21, SHIPPED DRY-RUN).** Aggregator rows rot the same way with no retraction (`stale_scrapes` was 138 on 2026-08-08), and the EventON feed does enumerate a bounded forward window with stable ids: one AJAX POST per month with `fixed_month`/`fixed_year` + a `focus_*_date_range` unix pair, answered by one unpaginated JSON array whose every entry carries a numeric `event_id` (written to `source_event_id` on every row). So the same primitive attaches — with a **strictly narrower ownership test**, because a corridor-wide source has corridor-wide blast radius. `org_slug` cannot answer "who owns this row": it is written only on INSERT while `buildStrongMatchUpdate` overwrites `event_url` + `source_event_id` when an organizer scraper merges into a resident row, so `org_slug='gocalaveras'` means "GoCalaveras inserted it once", not "GoCalaveras still maintains it". `ownsGoCalaverasRow` therefore requires **all** of: a bare-numeric EventON `source_event_id` (any other scheme is an organizer's key, written over ours), an `event_url` that is null or on gocalaveras.com (an organizer domain means that merge, or an EventON listing whose only link is the organizer's `_evcal_exlink` — indistinguishable here, so both are spared), a usable key at all (**unlike the pub sweep, a key-less row is never swept** — it can never be proven present, so an aggregator sweep would select it every run forever), and a venue/name not on the `manual-sources.ts` blocklist (those are filtered out of the batch, so their ids never enter the presence set). Two more aggregator-specific rules: **presence is measured against the RAW feed enumeration**, not the batch we write — an event dropped by the corridor filter, the blocklist, or the cross-source LLM dedup is still an event GoCalaveras lists, and treating our own filtering as the source's retraction would delete every corridor event a venue scraper also covers; and a month contributes a window only when its payload **proves it is that month** (≥⅔ of returned start dates inside the requested month, catching a feed that ignores `fixed_month` and echoes another one) and did not hit a display cap declared by the page's own `data-sc` shortcode (`detectShortcodeCap`, since a truncated tail looks exactly like a retracted one; cap-shape matching has burned twice in prod — `show_limit_paged=1`, a pagination toggle, read as a cap of 1 on 2026-08-11, then `jumper_count=5`, the month-jumper dropdown size, read as a cap of 5 for three runs after the toggle floor shipped — so values below `MIN_PLAUSIBLE_CAP` are toggles, `jumper_*` keys are denylisted UI chrome, and every cap-shaped key logs one disposition line — kept, toggle, or ignored — because a silently-withheld window is an invisibly inert sweep and each episode was diagnosed one masked key at a time). Slug keys are secondary, best-effort (regexed out of the response HTML), and **anchored to `/events/<slug>`** — EventON appends an occurrence tail to a recurring series permalink (`/events/mimosa-sundays-at-ironstone-vineyards/var/ri-13.l-L1`, live on four Ironstone rows), so keying on the last path segment would both invent a key the feed never emits (the row reads as retracted while plainly still listed) and collide across every series sharing an occurrence index; a run whose permalink extraction is thin (`slugExtractionHealthy`) also leaves id-less legacy rows alone, and a URL that yields no slug is not ownership. The month floor is **15**, not the primitive's single-venue 3: live months run 136/114/60/13/16/4, and a 4-listing far-future month cannot distinguish a truncated payload from a quiet one, so the thin tail intentionally contributes no window until it fills in. The sweep also passes a per-source `maxPerRun` of **10**, because at 169 resident rows the relative cap is pinned to the flat 20 (~12% of the aggregator's catalog deletable nightly). Locked by `scripts/test/gocalaveras-sweep.test.ts`. **`SWEEP_EXECUTE` is a per-source allowlist with no all-sources value** (`sweepExecuteEnabled`) precisely so graduating the organizer sweeps cannot arm this one. Review a few days of the `Sweep DRY-RUN would remove:` lines before adding `gocalaveras`; if that first honest report is a big backlog it needs a reviewed one-off purge, since the cap makes the sweep a steady-state maintainer, not a drain.

## Event Verification

Aggregator scrapers (e.g., GoCalaveras) occasionally get event dates wrong. For organizers we trust as canonical (e.g., Arnold Rim Trail), we cross-check scraped data against the organizer's own events page.

- `hwy4_orgs.canonical_url` — official events URL for the org
- `hwy4_orgs.canonical_check_enabled` — opt-in flag (default false)
- `hwy4_orgs.match_patterns` — substrings to identify the org's events when `org_slug` points at an aggregator
- `hwy4_events.verification_status` — `unchecked | verified | needs_verification | dismissed`
- `/api/verify-events` runs daily; fetches each canonical URL once, asks Haiku to confirm each event's date appears on the page
- **Time-drift detection (2026-07-25).** The same run also compares our stored `start_time` against the time the organizer's page states, because a date-only check cannot catch the failure that motivated it: the Arnold Rim Trail sunset hike verified fine in April, ART moved the start five days before the event, and nothing ever looked again. Two changes: (1) the verdict carries `page_start_time` / `page_end_time` lifted **verbatim** from the page, compared via the pure `compareEventTime` in [lib/verify-times.ts](lib/verify-times.ts) (locked by `scripts/test/verify-times.test.ts`); (2) the run now also **re-checks** already-`verified` events inside `RECHECK_WINDOW_DAYS` (10) whose last check is older than `RECHECK_STALE_DAYS` (3), so a time moved after the first check is caught as the date nears. `needs_verification` / `dismissed` rows are excluded — they're awaiting a human. **Never-guess:** a page that states no time flags nothing (`compareEventTime` returns `unknown` when either side is absent or ambiguous — e.g. a bare "6" with no meridiem, or a "11-1pm" range whose start meridiem can't be inferred). A `times_locked` row is skipped entirely: it's authoritative, so a page that disagrees is the page being stale. The organizer's time is staged on the row (`verification_suggested_start` / `_end`, migration `20260725b_verification_time_suggestions.sql`) and **never auto-applied** — `/admin/verification` shows an ours-vs-theirs panel plus a one-click **"Use H:MM (locks it)"** button (`applyOrganizerTime`) that writes the time and sets `times_locked` so the aggregator can't restore the stale value. Slack calls out the time-drift count separately from date flags.
- **Recurring programs are the dominant false positive.** A venue's events page routinely omits its weekly regulars: Murphys Wine & Beer Garden lists Wine-Down Wednesdays, Wine Blending Night and its concert series, but not its weekly trivia — so the verifier correctly reports "not on the canonical page" for trivia, and would keep reporting it (23 rows across two source names, each surfacing separately as it rolls into the 14-day window). **"Absent from the page" does not mean "not happening."** `/admin/verification` therefore has a **"Dismiss whole series"** action (`dismissEventSeries`) that dismisses every upcoming occurrence in one click, mirroring how `/admin/posters` approve applies to a whole recurring event: `isSameEvent` returns false across different dates by design, so `seriesIdentity` omits the date to compare the *series* instead. Measured 2026-07-27: 46 of ~56 enrolled-and-eligible events are recurring, so without this the queue would fill with the same finding forever.
- Flagged events show **nothing on the public site** (the "Date unconfirmed" badge was removed 2026-07-05 — it undermined reader trust). The flag is operator-facing: `/api/verify-events` posts a Slack alert (`SLACK_WEBHOOK_URL`) listing newly flagged events, and they queue up at `/admin/verification` (and the admin Inbox) for manual review (confirm / dismiss / hide / delete)

Currently enabled: **Arnold Rim Trail** (`arnoldrimtrail.org/events/`), **Murphys Wine & Beer Garden** (`murphyswinebar.com/events`, 47 upcoming) and **Brice Station** (`bricestation.com/collections/events`, 8 upcoming) — enrolled 2026-07-25. Add more orgs by setting `canonical_url` + `canonical_check_enabled=true` (plus `match_patterns` if upstream scrapers tag the org's events with an aggregator's `org_slug`).

**Audit a canonical page BEFORE enabling it — most fail.** `/api/verify-events` does a plain server-side `fetch` and strips tags (no JS execution), then asks Haiku whether each event appears. A page that is not a real, complete, server-rendered dated listing flags *every* one of that org's events as missing, burying the queue in false positives and training the operator to ignore it. That is worse than leaving the org unenrolled. Check by fetching the page, applying the same strip (`<script>`/`<style>`/`<noscript>` then all tags), and confirming per-event **dates** survive; **times** are a bonus (their absence is safe — `compareEventTime` returns `unknown` and never flags). ## Scraped description hygiene (reseller junk)

Concert listings that reach us through ticket-reseller pages arrive with junk a calendar-widget stripper was never built to see. All three shapes shipped live on Ironstone shows and were hand-cleaned once (2026-07-16) before coming straight back on the next scrape, which is why the fix lives in the shared sanitizer rather than in a curator's afternoon (HWY-11, 2026-07-27).

**The scrub runs inside `sanitizeDescriptionDetailed`** ([lib/description-quality.ts](lib/description-quality.ts)), so it covers **both** the write boundary (`normalizeEventLocation` in `scripts/lib/dedup.ts`, the hook every `upsertEvents` source calls) and every render path (`displayDescription` / `gateEventDescription`). A stored row therefore stops showing junk on the next revalidation, without waiting for a re-scrape or a backfill. Four passes, in order:

1. **Markdown artifacts** the extractor left literal, usually wrapped around a keyword-stuffed phrase (`This is **Gene Simmons - Murphys Murphys**`). `**`/`__` must wrap real content on one line, so a stray asterisk (a footnote marker, `free* (*with a paying adult)`) survives.
2. **Fake-local venue appositive** — `in Murphys, a local favorite for live entertainment`, `at Ironstone Vineyards-one of the area's go-to spots`. A voice violation as much as a quality one: the neighbor voice is ours and it is earned (`content/VOICE.md`). Deliberately narrow — the phrase alone is not the problem, the **appositive** is, so it must hang off a comma or dash and run to the end of its sentence. The delimiter set **excludes `:`** because the Rotary listing's "Live Music: Local favorites The Fabulous Off Brothers" would otherwise be eaten. Verified against every live row a naive phrase match would hit (the farmers market's "shopping your favorite local vendors", the craft fair's "one of our favorite events of the year"): none match.
3. **Doubled town name** (`Murphys Murphys`). Scoped to the event's **own town**, not any doubled word: genuine reduplicated place names exist (Walla Walla, and this is wine country), so a blanket rule would eventually eat a real one. `sanitizeDescription(text, { town })` — callers without a town simply skip this pass.
4. **Ticket-resale links** (`TICKET_RESALE_HOSTS`) are stripped outright, along with the dangling "Tickets at ." they leave behind. A reader following one can only be overcharged for a show whose venue sells directly (regtixs.com was the live case).

**The link rule is a denylist, not the allowlist it looks like it should be.** Checked against live data first: all 22 URLs then sitting in upcoming descriptions were legitimate — organizer sites (murphyscreektheatre.org, angelsmurphysrotary.org) and real sellers (ticketleap.com, onecau.se) — and an allowlist would have deleted every one, since the sanitizer is a pure function with no view of the org/venue registry. Stripping good links to catch bad ones is the worse trade. The whack-a-mole gap is closed by **flagging** instead: `findSuspectTicketLinks` ([lib/audit-checks.ts](lib/audit-checks.ts)) reports a daily `suspect_ticket_links` count for any *ticket-selling* URL whose host is neither a known reseller nor in `KNOWN_TICKET_HOSTS`. A human then adds the host to whichever list it belongs in. Plain organizer links are not ticket-ish and stay quiet.

Locked by `scripts/test/description-quality.test.ts` and `scripts/test/audit-checks.test.ts`, both of which assert what must **survive** as hard as what gets removed. Ship-time dry run over every distinct at-risk live description: 1 changed (the junk row), 7 byte-identical.

## Event Pricing (cost_tier)

Some events charge admission (Brice Station concerts, ticketed festivals). The fee is often present in the scraped `price` free-text or buried in the description, but free-text can't drive a badge or filter — so we derive a typed signal.

- `hwy4_events.price` — human-readable amount string (`"$25"`, `"Pay what you can"`). Unchanged.
- `hwy4_events.cost_tier` — typed enum: `free | paid | donation | varies | unknown`. The handle the UI keys off.
- `hwy4_events.price_extracted_at` — when `/api/extract-prices` last processed the row (NULL = queue candidate).
- `hwy4_events.price_locked` — manual override (mirrors `importance_override`). When `true`, `price` + `cost_tier` are human-set and **no automated writer touches them**: `/api/extract-prices` skips locked rows, and the scraper (`scripts/lib/dedup.ts`) omits `price` from every update payload (exact-match, fuzzy-merge, serial + batched paths).
- `hwy4_events.description_locked` — sibling to `price_locked` for the free-text `description`. When `true`, the scraper (`scripts/lib/dedup.ts`) omits `description` from every update payload, so a hand-edited description survives re-scrapes.
- `hwy4_events.poster_locked` — sibling to `price_locked` / `description_locked` for `image_url`. When `true`, the image is human-pinned (curator found a great poster) and the scraper omits `image_url` from every update payload (exact-match, fuzzy-merge, serial + batched paths). Use when a scraped or manually-found image is exactly right and must not be overwritten. Set via SQL: `UPDATE hwy4_events SET image_url='...', poster_locked=true WHERE id='...'`. To lock without changing the image: `UPDATE hwy4_events SET poster_locked=true WHERE id='...'`. Same caveat as `price_locked`: new rows for recurring events start unlocked. Use when the source's prose carries something stale that re-scrapes keep restoring — e.g. Ironstone "Mimosa Sundays", whose GoCalaveras description literally says "$15 each". Set via SQL: `UPDATE hwy4_events SET description=…, description_locked=true WHERE …`. Same per-row caveat as `price_locked`: new rows for a recurring event start unlocked. Use this when a source's listed price is wrong or stale and re-scrapes/extraction would otherwise keep restoring it — e.g. Ironstone "Mimosa Sundays", whose description literally says "$15 each" so extract-prices re-lifted $15 every run. Set via SQL: `UPDATE hwy4_events SET price=…, cost_tier=…, price_locked=true WHERE …`. **Caveat:** the lock is per-row. A recurring weekly event keeps getting *new* rows inserted for future dates; those start unlocked, so a stale price can reappear on the newly-scraped Sundays and they need re-locking (re-run the same UPDATE periodically).
- `hwy4_events.times_locked` — sibling to `price_locked` / `description_locked` / `poster_locked` for `start_time` + `end_time` (migration `20260725_add_times_locked.sql`). When `true`, the times are authoritative (human-set, or applied from the organizer's own canonical page) and **no automated writer touches them**: `scripts/lib/dedup.ts` omits both columns from every update payload (exact-match, fuzzy-merge, serial + batched), `rowChanged` stops counting a time diff as a change, and the self-contained `/api/scrape-moose-lodge` route strips them too. Added 2026-07-25: the Arnold Rim Trail sunset hikes were 30 minutes wrong on the day of the hike because the organizer moves the time as sunset shifts while our aggregator-sourced row was frozen at the April scrape — and there was previously **no way to pin a corrected time**, since every scraper wrote `start_time` unconditionally. Set via SQL: `UPDATE hwy4_events SET start_time=…, end_time=…, times_locked=true WHERE id=…`; unlock with `times_locked=false`. Same per-row caveat as the others: new rows for a recurring event start unlocked. Locked by `scripts/test/times-locked.test.ts`.
- `/api/extract-prices` runs daily; reads description+name and lifts **explicitly-stated** fees via Haiku. Never guesses an amount — no fee text means `cost_tier='unknown'`, not free. Skips `price_locked=true` rows.
- The public site shows a green **"Free"** badge or a **"$25" / "Ticketed" / "Pay what you can"** cost badge on each event card (scan-level), plus a **"Free"** quick filter on the homepage. `unknown` shows nothing.
- Backfill the whole upcoming queue by hitting the route repeatedly (it's idempotent via `price_extracted_at`): `curl -H "Authorization: Bearer $CRON_SECRET" "https://hwy4events.com/api/extract-prices?limit=150"`.

## Outbound Event Links

The "Visit Event Page" button links to a **destination derived from event identity, not scrape provenance**. See `PRD-event-link-resolution.md`.

**Priority order (first hit wins):** organizer canonical → venue canonical → stable-source `event_url` → GoCalaveras fallback → none (community / no source).

- **`lib/event-link.ts`** is the single source of truth: `resolveEventLink(event, { org, venueUrl })` resolves in the priority order above. `matchOrgForEvent(event, orgs)` maps an event to its organizer by `org_slug` (only when that org has a `canonical_url` — an aggregator slug like `gocalaveras` deliberately falls through) or by `hwy4_orgs.match_patterns` (normalized substring; enumerate spelling variants — the source really lists "Aronld Rim Trail"). Locked by `scripts/test/event-link.test.ts`.
- **Venue canonical (priority #2) is `hwy4_venues.website`, gated by `promotableVenueUrl(venueName, website)`** (2026-06-06 — the path existed since 2026-05-30 but was never fed any data; it was dead code until the detail page started passing `venueUrl`). A venue website only promotes to a durable CTA for **single-operator** venues: `isMultiTenantVenue()` rejects parks / community centers / town squares / fairgrounds / amphitheaters (no single events page exists, and the auto-matched Places website is often a generic homepage or a flat-wrong match — Perry Walther Community Center matched a Bear Valley parents group), and social-page websites (Facebook/Instagram/X) are rejected too, as are **aggregator/unstable-host** websites (Google Places sometimes syncs a GoCalaveras listing in as a venue's "website" — e.g. Angels Camp Museum — and a non-durable host is never a durable destination). So e.g. Stevenot Winery + Murphys Wine & Beer Garden events resolve to the venue site; a Murphys Community Park event keeps the GoCalaveras fallback. Both helpers are shared by the detail page and the `/api/check-events` audit so the page and the KPI can't disagree. Promotion needs the event's `venue_key` populated (no key → no venue lookup → falls through to the source/fallback).
- **`UNSTABLE_SOURCE_HOSTS`** (currently `gocalaveras.com`) are aggregators whose per-event links 403 server-side validators but return 200 in a real browser. **`AGGREGATOR_FALLBACK`** (`true` as of 2026-06-03): a GoCalaveras event with no organizer/venue match renders that GoCalaveras link as a **non-durable** (`durable:false`) source. **The detail page scales source prominence to durability** (2026-06-21): a durable organizer/venue/stable-source link gets a high-contrast outline **"Visit … ↗"** button in the action rail (the conversion CTA), while a non-durable aggregator link renders as a quieter attributed **"Listed on {host} ↗"** line (`sourceHostLabel`) — source *presence* is universal (credibility + an accuracy safety valve so a reader can verify if our data is wrong), but only durable links earn button weight. Share stays the sole filled primary (the only growth loop); on mobile the Visit button is a secondary outline, never co-equal. Community submissions are excluded. The link is **kept out of JSON-LD** (`offer.url` always uses our own stable event page when `durable:false`) so a potentially-churnable permalink never leaks into structured data. **Defense in depth (2026-06-21): an unstable host is never durable in ANY slot.** A misconfigured `hwy4_orgs.canonical_url` or `hwy4_venues.website` that is *itself* a GoCalaveras URL can't launder a churnable link into a durable CTA (or into JSON-LD): `resolveEventLink`'s organizer branch skips a canonical whose host `isUnstableHost`, and `promotableVenueUrl` rejects an unstable venue website. Real cases caught: the `the-stitch-lounge` org row (canonical was a GoCalaveras permalink) and the `angels-camp-museum` venue (Places-synced GoCalaveras "website") — both now resolve to `null`/non-durable. Locked by `scripts/test/event-link.test.ts`. Both rows were also cleaned in the DB (2026-06-21: org `canonical_url` nulled; venue `website` nulled + `places_locked`). **Write-time guard too:** `/api/sync-venue-facts` drops an `isUnstableHost` website on every sync (`website: details.websiteUri && !isUnstableHost(...) ? ... : null`), so Google Places can't re-store a GoCalaveras "website" on any venue — the stored data stays clean, not just the read path.
- **Consumers** (all import the resolver, none read `event_url` directly for a destination): the event detail CTA + its JSON-LD `offer.url` ([app/events/[slug]/page.tsx](app/events/[slug]/page.tsx)), the patriotic detail layout, and `buildEvent` in [lib/schema.tsx](lib/schema.tsx) (which points `ItemList` offers at the internal page). **The event cards** ([components/EventCard.tsx](components/EventCard.tsx)) deliberately render **no** outbound/provenance line (2026-06-22): a card's whole surface links to our own richer detail page, and source attribution ("Listed on GoCalaveras", durable "Visit …" buttons) lives there — duplicating it on every card added noise and leaked clicks off-site. The server-side `outboundLink` list-field was **removed 2026-07-01** (it had been computed on every cached row since 6/22 but rendered nowhere; its two per-cache-window context queries — `hwy4_orgs` + `hwy4_venues` — went with it). If a card ever needs an outbound link again, resurrect `buildOutboundLink`/`loadLinkContext` from git history. The three briefing/newsletter generators already link to internal pages, so they were always safe.
- **To give an organizer's events a durable link**, add the org to `hwy4_orgs` with `canonical_url` + `match_patterns` (no code change). That upgrades the event from the GoCalaveras fallback to the organizer's own site. `/api/verify-events` shares the same `matchOrgForEvent`, so date-verification and link resolution always agree on which org owns an event.
- **`validateEventUrls`** ([scripts/lib/validate-urls.ts](scripts/lib/validate-urls.ts)) skips `UNSTABLE_SOURCE_HOSTS` (a 403 from our server is not a dead user-facing link).
- **`/api/check-events` link-gap KPI.** The audit reports two things: `aggregator_fallback_links` (raw count of events whose best link is only the non-durable GoCalaveras fallback — trend signal) and `actionable_link_gaps` — **single-operator** venues with **≥5 upcoming events** using only the fallback (`GAP_VENUE_THRESHOLD` in the route). The audit applies the same `promotableVenueUrl` guard as the page (so venues that already resolve to a durable venue link drop off) and excludes `isMultiTenantVenue` parks/community-centers/town-squares from the actionable list (those have no single canonical events page — the fallback is their correct terminal state, so they're not "go add an org row" work; they still count in the raw trend number). Net: the worklist surfaces only genuine single-operator organizers (a new concert series, a winery, a bar) worth a ~10-min `hwy4_orgs` row. Watch `actionable_link_gaps`, not the raw count.
- **Decision (2026-05-30): do NOT build canonical auto-discovery.** The long tail is one-offs where the GoCalaveras fallback is correct. Only revisit if `actionable_link_gaps` climbs fast. To give an organizer a durable link, add its `hwy4_orgs` row by hand (canonical URL must be a page that renders server-side — JS-only calendars like `bigtrees.org/events/` are fine as a *link* but can't be enrolled in `canonical_check_enabled` date-verification).

## Venue Info (`hwy4_venues`)

The event detail page shows a venue section: a **local-voice blurb** (what the place is, the vibe, named specifics) plus a **live-facts strip** (rating, today's hours, phone, website). This serves the personas who want venue context (Miguel deciding if the drive is worth it, Jen checking logistics, Mia recommending to guests) without violating the "local voice, not corporate voice" rule — the prose is ours; only the factual strip is third-party.

- **`hwy4_venues`** — one row per registry venue, keyed by `venue_key` (the `scripts/lib/venues.ts` key). Columns: `canonical/town/address` (seeded from the registry), `blurb` + `blurb_generated_at` (local voice, **the only published voice copy — written by a human Save**), `blurb_draft` + `blurb_draft_at` (a **pending** machine draft awaiting review, never rendered publicly — Phase 1B), and Google Places facts (`place_id`, `rating`, `user_ratings_total`, `phone`, `website`, `maps_url`, `hours` JSONB of weekday strings, `places_attributes`, `places_synced_at`). RLS on, public read only.
- **`hwy4_events.venue_key`** — links an event to its venue row. Populated at write time by the scraper upsert (`scripts/lib/dedup.ts` via `resolveVenueKey` in `scripts/lib/venue-matcher.ts`) and backfilled by `scripts/backfill-venue-keys.ts`. NULL when the venue isn't in the registry → the detail page shows no venue section (graceful no-op).
- **Blurbs** are drafted by `scripts/draft-venue-blurbs.ts` (Opus). Sources, in priority: `places_attributes` (verified persona signals — stated plainly), live Google Places **review snippets** (vibe + named specifics only; fetched transiently, never quoted or stored), and `docs/LOCAL-KNOWLEDGE-BASE.md` (owners, history). Em-dash + banned-phrase enforced (incl. no internal-tooling references). Dry-run by default; `--apply` to write the published `blurb`; `--all` to regenerate; `--out <file>` to export proposals as JSON without touching the DB (used for the review-sheet workflow); pass venue keys to target specific ones. **Rob reviews before publish** — the script refuses to auto-write a blurb that trips a hard voice rule. ⚠️ Review-sourced names/dishes are lower-confidence than the knowledge base — sanity-check them.
- **Self-healing blurb queue (Phase 1B, the accuracy contract: a machine drafts, a human publishes).** `draft-venue-blurbs.ts --queue --apply` writes its draft to the **pending** `blurb_draft` column instead of the live `blurb`. The **Venue Blurb Drafts GitHub Action** ([.github/workflows/draft-blurbs.yml](.github/workflows/draft-blurbs.yml), **daily** 13:00 UTC, after the weekly Places sync) runs it for every venue missing a blurb. (Daily so a new venue gets a draft within a day of its `place_id` resolving, rather than waiting for the next Monday; the gate makes the off-Monday runs no-ops until there's new work.) The `--queue` gate is `blurb IS NULL AND blurb_draft IS NULL AND blurb_draft_at IS NULL AND place_id IS NOT NULL` — idempotent + self-limiting (steady state is a no-op). A curator reviews each draft at **`/admin/venues`** (the textarea pre-fills with the draft + an "AI draft, not yet published" banner): **Save** publishes it to `blurb` and clears the draft; **Discard** clears the draft text but **keeps `blurb_draft_at`** as a "human declined" marker so the drafter won't re-propose it. `blurb` is only ever written by a human Save — the machine never publishes voice copy.
- **Self-healing address queue (the same contract for street addresses).** The daily `/api/agent/draft-venue-addresses` cron (`lib/agent/draft-venue-addresses.ts`) does for `address` what the blurb queue does for `blurb`: for any venue with no `address` (and not `places_locked`), it web-researches the Tier-A street address (`lib/agent/research-venue.ts`) and stages it as a **pending** `address_draft` (+ `address_draft_at` marker + `address_draft_meta` of confidence/sources). The `/admin/venues` card shows the suggestion with its confidence + sources: **Apply** writes the live `address` (and surfaces a copyable `scripts/lib/venues.ts` snippet to commit); **Discard** clears the suggestion but keeps `address_draft_at` as the "human declined" marker so it isn't re-researched. The machine never writes the live `address` — a human Apply does. Columns added by migration `20260630_venue_address_drafts.sql`.
- **Local knowledge capture (the KB feedback loop).** A human Save at `/admin/venues` is the highest-trust knowledge the system ever sees, so it's persisted to **`local_facts`** (migration `20260701_local_facts.sql`; provenance-carrying, service-role RLS — the structured companion to the prose `docs/LOCAL-KNOWLEDGE-BASE.md`, the same two-layer "markdown for humans, Supabase for agents" pattern PAOS uses for travel + the knowledge graph). `saveBlurb` records the approved blurb via [`lib/local-facts.ts`](lib/local-facts.ts) `captureBlurbFact` with `confidence='human'`, storing the AI `blurb_draft` it replaced as `prior_value` + a `was_edited` flag (the correction signal); a re-save supersedes the prior active fact so "active" is always current. The blurb drafter reads active facts back in (`getActiveFacts`) so a regeneration (e.g. a cleared-then-requeued venue) preserves what a person already vetted. Best-effort: a capture error never blocks the publish. Pure core locked by `scripts/test/local-facts.test.ts`. Blurbs published **before** the capture loop shipped (2026-07-01) were never recorded; `scripts/backfill-local-facts.ts` (dry-run / `--commit`) backfills one active `source='backfill'`, `confidence='human'` blurb fact per published-blurb venue with no active fact — idempotent (skips already-captured venues), reversible (`DELETE FROM local_facts WHERE source='backfill'`), executed against prod 2026-07-11. Future sources (submission-triage `new_info`, manual entry) plug into the same table without a schema change; a read/management UI is the next slice.
- **`places_attributes`** (JSONB) — factual Places attributes (dogs / kids / groups / outdoor / live music / parking / type) refreshed weekly by `/api/sync-venue-facts`. Grounds blurbs **and renders as a practical badge row** on the event detail page (Phase 2 — `practicalBadges` in [components/VenueInfo.tsx](components/VenueInfo.tsx) curates the decision-driving few: dog-friendly / kid-friendly / patio / groups / parking; Tier A, attributed to Google via the rating's "via Google" label). Review text is never stored (Google ToS).
- **Live facts** come from `/api/sync-venue-facts` (weekly cron, Google Places API New). `place_id` is cached indefinitely; rating/hours/etc. refresh weekly. The UI attributes the rating to Google (links to `maps_url`, "via Google" label) as required by Google's terms.
- **`places_locked`** — when `true`, `/api/sync-venue-facts` skips the venue entirely. Set it (and null the facts) for venues with no *correct* Places listing so the weekly sync can't re-match a wrong one: permanently-closed venues (Twisted Oak), venues with no distinct listing (The Poor House), and private/no-own-listing spots (the Blue Lake Springs amphitheater/pool/lake, which otherwise all collapse onto the one HOA listing). Mirrors `hwy4_events.price_locked` / `description_locked`. To pin a *correct* listing instead, set `place_id` + null `places_synced_at` and let the next sync re-fetch.
- **Adding/refreshing a venue:** add it to `scripts/lib/venues.ts`, then `cd scripts && npm run seed-venues` (registry → `hwy4_venues`), and re-run `npm run backfill-venue-keys -- --apply` so existing events link to the new venue. **Everything else self-heals daily, no manual step needed:** the new-venue Places onboarding (`/api/sync-venue-facts?only=new`, 11:30 UTC) fills `place_id` + facts; the blurb drafter (1pm) auto-queues a `blurb_draft` into `/admin/venues`; and the address drafter (`/api/agent/draft-venue-addresses`, 10am) stages an `address_draft` if the registry had no address. Review/approve the blurb + address suggestions at `/admin/venues`. (Manual fast-paths still work: `npm run draft-venue-blurbs -- --apply`, `curl .../api/sync-venue-facts?only=new`.)

## Weather (event chips)

Every event card and the event detail page show a small weather chip — built this session from the dormant module in Peter Hollens's Eugene fork, then rebuilt for the corridor. Three design calls drove it: **per-town** (elevation), **event-hour** (time-accurate), **every event** (no outdoor gate).

- **Source: NWS, free, no API key.** [lib/weather.ts](lib/weather.ts) `getForecast(lat, lng)` resolves the NWS grid (`/points`) then pulls the **hourly** forecast (`/forecastHourly`), folding it (`foldHourly`) into `byHour` (keyed `YYYY-MM-DDTHH` Pacific) plus a `byDate` summary derived from the same periods (no second request). Fetches use Next's `revalidate` cache (points 24h, forecast 1h) and a descriptive `WEATHER_USER_AGENT` (NWS requires it; `lib/constants.ts`).
- **Per-town, by elevation.** Copperopolis (~850 ft) and Bear Valley (~7,000 ft) are ~60 mi / 6,000 vertical ft apart, so one corridor-centroid forecast is wrong at both ends (Copperopolis 83° vs Bear Valley 69° on the same afternoon). `getForecastsByTown()` fetches one forecast per town from the lat/lng in **[lib/towns.ts](lib/towns.ts) (`CORRIDOR_TOWNS`)** and returns a `TownForecasts` map (town name → `Forecast`). NWS responses are cached by URL, so every page reuses the same ~9 cached fetches (no extra API load).
- **Event-hour temp, not daily high/low.** `resolveEventWeather(forecast, event)` returns the temp/condition at the event's **start hour** (`byHour[date+hour]`), falling back to the day's high when an event has no start time. (The old daily-high/overnight-low heuristic made a 6pm concert read the 5am low of 55°; now it reads ~74°.)
- **Long-event range.** When an event spans **≥4 hours (`LONG_EVENT_HOURS`) AND the temp swings ≥12°F (`SWING_THRESHOLD_F`)**, `resolveEventWeather` returns a `range {low, high}` instead of a point; the chip renders `60→85°` and the qualifier becomes **"bring layers"**. Short or flat-temp events keep the single number; the chip decides automatically. Designed via `/brain steve-jobs` (the spread is the evidence, the verb is the product; never an hour-by-hour strip).
- **Shown on every event — no outdoor gate.** The chip appears whenever a forecast exists for the event's town+date. (The old outdoor-gate module `lib/is-outdoor-event.ts` has been deleted; resurrect from git if a gate is ever wanted back.)
- **`weatherQualifier`** ([lib/weather-conditions.ts](lib/weather-conditions.ts)) tags the chip from the event-hour reading: `rain likely` (≥50% precip) / `showers possible` (≥30%) / `bring layers` (long-event range) / `patio weather` (≥80° clear) / `bring a layer` (≤50°). Rain/storm/snow swap the icon (`conditionIcon`) and tint it (`conditionColorClass`); `mapShortForecast` maps NWS text → a `ConditionKey`. **Known gap:** snow currently borrows the "rain likely" wording (icon is correct) — irrelevant until winter Bear Valley.
- **`WeatherChip.tsx`** renders a single temp or a `low→high` range + the qualifier. (The old multi-day `WeatherStrip.tsx` was removed; the `byDate` summary + `getWeatherForDate` helpers remain in `lib/weather.ts` for any future multi-day use.)
- **Wiring (the forecast threads server→client as a prop):** `app/page.tsx` + `components/EventList.tsx` (homepage); `components/SimpleEventList.tsx`, fed by `components/TemporalEventsView.tsx` (the `/this-week|weekend|month` pages) and `app/towns/[slug]/page.tsx` (town pages, a one-town map); and `app/events/[slug]/page.tsx` (detail page, a "Weather" row in the meta `<dl>`, `size="detail"`). The bespoke detail layouts (Patriotic/AdoptAPet/ClassicRock) don't show weather.

## Search Console (SEO analytics)

Google Search Console is the top-of-funnel demand signal (what people search to reach us — the visitor-acquisition channel, Miguel in BUSINESS-PLAN). Wired live 2026-07-05. Same two-layer shape as the rest of the cockpit: a dumb collector writes rows, a pure lib shapes insight, and two consumers (a human panel + the Growth Agent) read it.

- **Auth (service account, no OAuth):** `lib/agent/gsc.ts` signs a service-account JWT with Node's built-in crypto (zero deps), exchanges it for a `webmasters.readonly` token, and queries the Search Analytics API. SA = `gsc-reader@hwy4events.iam.gserviceaccount.com` (project `hwy4events`), added as a **Full** user on `sc-domain:hwy4events.com`. Key: `~/.config/hwy4/gsc-reader.json` locally + `GOOGLE_SEARCH_CONSOLE_SA_JSON` in Vercel (see Environment Variables). Site defaults to `sc-domain:hwy4events.com` (`GOOGLE_SEARCH_CONSOLE_SITE_URL` to override). `fetchGscCuts(windowDays, historyDays)` returns three cuts (date / query / page), null when the env is unset.
- **Collector:** `/api/agent/collect-seo` (daily 11:00 UTC) writes `seo_snapshots`. New columns (migration `20260705_seo_snapshots_enrich.sql`): `dimension` (`date | query | page | query_page` legacy) + `data_date`. The **by-date** cut is the durable trend spine, **upserted** on a plain `UNIQUE(source, data_date)` (NOT partial — PostgREST `onConflict` can't name a partial predicate; query/page rows carry `data_date = NULL` and Postgres treats NULLs as distinct, so they never collide). by-query / by-page are point-in-time inserts read at their latest `captured_at`. Service-role only (RLS unchanged). Backfill via `?history=480` (the route's own knob — no separate script).
- **Insight (pure, tested):** `lib/seo-insights.ts` — `selectStrikingDistance` (page-1/2 fringe, position ~4–20 with impressions, ranked by un-captured impressions), `monthOverMonth` (last 28d vs prior 28d, split by count so GSC gaps don't skew), `snapshotTotals`. Locked by `scripts/test/seo-insights.test.ts`. `lib/seo-data.ts` `getSeoOverview(supabase)` reads the three cuts (each bounded < 1,000 rows, so no PostgREST truncation) and returns the shaped `SeoOverview` both consumers use.
- **Consumer 1 — human panel:** `/admin/analytics` **Search (Google)** group (28d totals with MoM deltas, striking-distance list, top queries, top pages, clicks-per-day trend). Ordered striking-distance-first (the highest-leverage work).
- **Consumer 2 — Growth Agent:** `lib/agent/growth-context.ts` feeds the memo's `seo` signal (totals + MoM + top + striking); the growth-memo prompt treats the top striking query as a prime move-of-the-week and drafts the specific page change. The chief-of-staff digest reads the latest by-query snapshot (filtered `dimension='query'`).

## Region parameterization (engine/instance split)

The engine is region-parameterized so it can run as N deployments off one repo (BUSINESS-PLAN §6: Calaveras is the beachhead, the 30A/Los Gatos port is the monetization). **The full contract lives in [docs/REGIONS.md](docs/REGIONS.md)** — read it before touching anything region-shaped. In brief:

- **`regions/<slug>/core.ts`** (client-safe: brand + geo + timezone) and **`regions/<slug>/ops.ts`** (server-only: emails, SEO, schema.org, newsletter chrome) hold every region-specific value as pure data. Registries: `regions/index.ts` + `regions/ops.ts`. The env var picks the active region; unset → `calaveras`.
- Engine code reads exactly two accessors: **`lib/region.ts`** (core) and **`lib/region-ops.ts`** (ops). **Never import `lib/region-ops.ts` from a client component** — it must stay out of public bundles.
- Region modules are **pure data, zero runtime imports, relative import paths only** — they load in client bundles, the edge runtime (middleware, `/og`), and the `scripts/` tsx runner alike.
- `requireRegion("calaveras")` in [lib/cron-auth.ts](lib/cron-auth.ts) gates the region-specific crons (the 4 venue-schedule watchers + `scrape-bls` + `scrape-moose-lodge`) so they no-op on other regions — `vercel.json` is shared across deployments. No-op on Calaveras.
- `next.config.ts` image `remotePatterns` stay hardcoded (an instance file) but are pinned equal to the union of every region's `imageHosts` by `scripts/test/image-hosts.test.ts`.
- **This is an in-progress program.** Landed: the config seam + brand/domain/email/UA/timezone threading (this doc). Planned (see docs/REGIONS.md): the LLM prompt + `content/VOICE.md` split, the content packs (town/intent/holiday/faq prose), and the `scripts/lib` pipeline data (venue registry, manual-source blocklist, corridor arrays). Explicitly out of the program: `lib/tables.ts`, table/type/column renames, the Supabase project move.

## Database security posture

The Supabase project is **shared** (hwy4-events + PAOS + BrainsFor), so a security-advisor run returns other tenants' findings alongside ours. Before acting on one, check whether the object is hwy4's: `home_todos_touch_updated_at`, `handle_new_user`, `search_brain_atoms`, and the `pack_downloads` / `pack_events` policies are **not** — fix those from `~/rob-ai`. Migration `20260815_security_lints.sql` closed the 15 that were ours, and three of its findings are standing rules:

- **`revoke ... from public` does not revoke from `anon` / `authenticated`.** Supabase's default privileges grant EXECUTE **explicitly** to both roles on every new function in `public`, and an explicit role grant survives a revoke aimed at `PUBLIC`. `20260621_gate0_stats_rpc.sql` and `20260621b_growth_signal_rpcs.sql` both did this and their headers claimed the functions were service-role-only; the live ACL said `{postgres=X, anon=X, authenticated=X, service_role=X}` for 7 weeks. Always name the roles: `revoke execute on function public.f(args) from public, anon, authenticated;`. Verify with `select proacl from pg_proc where proname = '…'` — the ACL, not the migration text, is the source of truth. Same trap applies to any new RPC.
- **A public form's RLS INSERT policy is a liability, not a feature, when the route uses the service-role key.** Every writer of `event_submissions` and `newsletter_subscribers` is a service-role route, which bypasses RLS entirely — so the old `with check (true)` policies granted the app nothing and granted anyone holding the (publicly-shipped) anon key a direct PostgREST write path around the honeypot, the per-email rate cap, and validation. Both are dropped; **RLS enabled with zero policies is the intended end state** for these tables, and the resulting `rls_enabled_no_policy` INFO lint is expected. Don't "fix" it by adding a policy back.
- **`hwy4_events`' `Public read using (true)` is load-bearing — do not narrow it to `visibility = 'public'`.** It reads like an over-broad policy (anon can read ~233 members-only Blue Lake Springs / Moose Lodge rows) but the Clubs filter is applied **client-side**: [lib/events-data.ts](lib/events-data.ts) fetches private rows on purpose via `.or("is_routine.neq.true,visibility.eq.private")`. Tightening the policy empties the Clubs view. The duplicate `Public can read upcoming events` policy was deleted as dead (permissive policies OR together, so it could never narrow anything).

Also: `pg_trgm` and `btree_gist` now live in the `extensions` schema, and every hwy4 function in `public` pins `set search_path = ''` with schema-qualified table references. Match that in any new function — an unpinned one is an advisor finding on the next run.

## Living Documents Registry

## UI Standards

- **Cursor:** Every `<button>` and clickable non-`<a>`/non-`<Link>` element MUST include `cursor-pointer` in its Tailwind classes. Tailwind v4 does not set `cursor: pointer` on buttons by default — the browser shows an arrow, which makes buttons look non-interactive.
- **Client bundle weight:** Avoid importing heavy libraries (date-fns, lodash, etc.) in `"use client"` components. Use `lib/date-utils.ts` for date formatting on the client. Heavy/non-critical components should be lazy-loaded with `next/dynamic`.
- **Hydration budget:** Links and navigation must work within 1–2s on mobile. Keep the client component tree shallow; prefer server components with small client wrappers (see `WeeklyBriefing.tsx` + `WeeklyBriefingTabs.tsx` pattern).
- **JSON-LD sinks:** every `<script type="application/ld+json">` must serialize via `serializeJsonLd()` in [lib/json-ld.ts](lib/json-ld.ts), never raw `JSON.stringify` into `dangerouslySetInnerHTML`. `JSON.stringify` leaves `<` unescaped, so scraped text containing `</script>` becomes stored XSS (Eugene fork security review 2026-07-02, `docs/research/2026-07-02-peter-security-handoff.md`). Locked by `scripts/test/json-ld.test.ts`.

### Voice rules specific to Hwy4Events copy

These reinforce SOUL.md and are non-negotiable for any user-facing copy on this site:

> **The machine-checkable version of these rules is [content/VOICE.md](content/VOICE.md)** — the voice constitution. It is mirrored in [lib/voice.ts](lib/voice.ts) (`VOICE_MD`, pinned identical by `scripts/test/voice-md-sync.test.ts`) and injected into **every** LLM generator via `withVoice()` (briefing, weekend briefing, newsletter, description extraction, venue blurbs, town content). `scripts/voice-lint.ts` enforces the lint-able subset against static content in CI. **Any new content surface (prompt or page) must inject `withVoice()` / pass `voice-lint` before launch.**

- **No em dashes.** SOUL.md rule. Use commas, periods, semicolons, parentheses. The Opus draft script at [scripts/draft-town-content.ts](scripts/draft-town-content.ts) enforces this in the system prompt and via post-generation check.
- **Don't generic-ify the geography.** Each town has specific venues, owners, landmarks, and character. Use them by name. "Newsome Harlow's fire pit" beats "a local winery's outdoor seating."
- **Verify cadence and hours claims.** Statements like "open every day" or "live music every Thursday" go stale and get quoted forever. Either link to the venue's site, hedge ("often", "most weeks"), or omit. Rule was added after the Murphys Irish Pub "7 days a week" hallucination on 2026-05-25. The knowledge base ([docs/LOCAL-KNOWLEDGE-BASE.md](docs/LOCAL-KNOWLEDGE-BASE.md)) is a draft input, not a verified source.
- **Named entities over generic descriptors.** Real owners (Chuck Hovey, River Klass, Siri & Rich Gilpin), real venues, real numbers. This is also the AEO win.
- **Q&A blocks should mirror real search queries.** First sentence of the answer fully resolves the question. Lift-able by answer engines.
- **The conference-dinner gut check:** would Rob actually say this out loud to another operator at a conference dinner? If it sounds like a marketing intern wrote it, kill the line.
- **Never reference internal tooling in public copy.** Words like "the knowledge base", "my notes", "my sources", "public info", or "the data" are plumbing — they mean nothing to a reader and break the neighbor voice. When there isn't much to say, punt like a human: "I've never been there" (only if true), "I don't have much on it yet", then point somewhere useful (the venue's site, the event details, or invite the reader to send the scoop). Enforced in the venue-blurb generator ([scripts/draft-venue-blurbs.ts](scripts/draft-venue-blurbs.ts)) via a hard prompt rule + banned-phrase check.
