## Newsletter email rendering ([lib/newsletter.ts](../../lib/newsletter.ts))

`buildEmailHtml(robNote, content, unsubscribeUrl)` is the single source of truth for the email HTML — both the Thursday send and the `?preview=1` route use it, so what you preview is what ships. Body + "From Rob" note are markdown-ish (`[label](url)` links) wrapped into `<p>` by `renderParagraphs`, which **normalizes CRLF→LF first** (admin-textarea edits arrive as `\r\n\r\n`, which a naive `split("\n\n")` misses and collapses into one block).

- **Layout:** 640px shell, 18px body / line-height 1.6, forest-green hero (`#1B3A2D`) with the site's Big Trees sequoias flanking the title + Millie peeking onto the cream below. Tuned against pro newsletters (Feed Me, Walk With History) — wider + larger type than the old 560/16.
- **Scannable spine:** `boldEventAnchors` bolds **dated** weekday anchors ("Friday, June 5", "Saturday the 6th") and the "Rob's Pick" lead-in (body only, not the From-Rob note). Render-time + deterministic, so it lands on every draft — including already-queued/edited ones — with no dependency on the model emitting markup. Bare day names are deliberately left unbolded.
- **Voice:** the generation prompt (`NEWSLETTER_SYSTEM_PROMPT`) treats the email as a **teaser, not the full calendar** — be selective, the site carries the complete lineup, the email earns the click.
- **Brand assets:** email clients don't render SVG, so the hero marks are PNGs in `public/email/` (`tree.png`, `millie-happy.png`), served from `SITE_URL` at send time. Regenerate from the site's SVGs with `node scripts/generate-email-assets.mjs`.
- **Scanner-safe funnel (2026-07-03):** `/api/newsletter/confirm` and `/api/newsletter/unsubscribe` render a read-only interstitial on GET and perform the action only on POST — mail-security scanners prefetch every GET in an email, and the old GET side effects let a scanner fake a confirm or silently unsubscribe a real reader on every Thursday send (a confirm-rate/subscriber leak). The unsubscribe POST doubles as **RFC 8058 one-click** (every send now carries `List-Unsubscribe` + `List-Unsubscribe-Post`, the Gmail/Yahoo bulk-sender requirement). First confirm sends a one-time **welcome email** (`buildWelcomeEmailHtml` in [lib/newsletter.ts](../../lib/newsletter.ts), best-effort so it never blocks the confirm; copy locked by `scripts/test/newsletter-welcome.test.ts`). **Confirm landing (HWY-43, 2026-09-12):** GET looks the token up (already-confirmed and unknown tokens render their own page instead of another button); POST success/failure stays on the route as HTML. The old 303 to `/?newsletter=confirmed` (and `invalid` / `error` / `already-confirmed`) was unread on the homepage, so a successful confirm looked like a no-op. Signup copy names the From + subject and the extra tap; already-confirmed resubmits no longer say "check your email." Confirm + reminder copy lives in [lib/newsletter-confirm.ts](../../lib/newsletter-confirm.ts), locked by `scripts/test/newsletter-confirm.test.ts`. Tokens do not expire. **Reminder drafts are human-gated:** `/admin/newsletter` lists pending-unconfirmed rows older than 24h (unsubscribed excluded, never invented) and opens a Gmail compose deep-link per address. The app does not send those, and there is no reminder cron.

## LLM link integrity (briefings + newsletter)

The three LLM-written surfaces (daily briefing, weekend briefing, newsletter) hand the model an exact `URL:` per event, but the model sometimes **reconstructs the URL from its prose rename instead of copying it** — it writes "[Kane Brown at Ironstone](…/kane-brown-murphys-2026-08-16-murphys)" for a row named "Ironstone Summer Concert Series", minting a plausible dead slug (three live 404s in the 2026-08-15 briefing, including the one link a reader actually clicked). It also **launders stale URLs from the RECENT BRIEFINGS freshness section** (re-dating a dead slug to a new occurrence), and an honestly-generated link **rots post-generation** when the row is renamed or merged later that day (the 2026-08-11 shrimp-feed hand merge orphaned `rotarys-annual-shrimp-feed-auction-…` while it sat in the stored weekend briefing and the already-sent newsletter). Three deterministic layers close all of it — same philosophy as `boldEventAnchors` and the newsletter click-tracking rewrite: never depend on the model emitting correct markup.

1. **Generation-time repair** — [lib/briefing-links.ts](../../lib/briefing-links.ts) (`repairEventLinks`, locked by `scripts/test/briefing-links.test.ts`) runs in all three generators before save: every internal `/events/` link must resolve against the exact event set that was in the prompt; a broken slug is re-mapped to the event it plainly meant (same date, and the link text/slug carries the event's name, act, or venue tokens; clear-winner rule, never guesses between rivals) or downgraded to plain text — a mention beats a 404. Repairing before save also keeps `briefing_history` clean, which is what stops the laundering loop. External links and non-event internal links are never touched. Repairs log `BRIEFING_LINK_REPAIR` / `BRIEFING_LINK_UNLINK` (greppable, the `URL_DATE_CORRECTION` idiom). The prompts also now forbid constructing URLs — but the prompt is a frequency reducer; the repair pass is the guarantee.
2. **Render-time self-heal** — the homepage ([app/page.tsx](../../app/page.tsx)) re-runs the same repair on both stored briefing texts against the live feed on every revalidation, so a link orphaned by a rename/merge *after* generation heals within one ISR window instead of waiting for the next generation. Only slugs dated inside the supplied feed's own window are judged, so links to days that scrolled out of the feed are never falsely unlinked. (Sent newsletters are immutable; layer 3 is their safety net.)
3. **Stale-slug fallback upgrades** — `pickFallbackEvent` in [lib/events.ts](../../lib/events.ts) gained two second-chance passes for minted/rotted slugs already in the wild (shared, indexed, emailed), both 301-ing at the detail page: **dominance** (a ≥0.5-score, ≥3-token partial name match with every rival ≤0.25 — the renamed shrimp feed) and **containment** (the slug carries ALL tokens of exactly one same-town candidate's act or distinctive venue core — `kane-brown-…` → the Ironstone series row via `artists`; `live-music-brice-station-vineyards-…` → the Deep Thicket row via venue). Ambiguity still 404s; locked by `scripts/test/events-fallback.test.ts`.

The stored texts carrying the 2026-08-15 dead links (`site_config` weekly/weekend/latest_newsletter, `briefing_history` 08-07 + 08-15, the sent `newsletter_drafts` rows) were repaired in place the same day.

## Rob's Picks in briefings + newsletter ([lib/briefing-picks.ts](../../lib/briefing-picks.ts), #356)

The daily briefing, weekend briefing and newsletter decide what a pick is with the homepage's own rule: `eligiblePickEntries` in [lib/picks.ts](../../lib/picks.ts) (public, not sold out, not ended, absorbed by a live `FESTIVAL_GUIDES` entry when one matches), extracted from `selectPicks` so the rule lives once. `selectBriefingPicks` windows it per surface (daily: today + 7 days via `dailyBriefingPicks`, a running festival included because it absorbs its nightly picks, no lookahead; weekend: Fri to Sun + one pick from the following 14 days; newsletter: from the send date, never before today (`generateNewsletter` takes it; a Wednesday-evening pick is over before the Thursday email lands) to the end of the 10-day read, + up to two picks from the following 21), and all three prompts share `ROB_PICKS_RULE` (the daily adds `DAILY_PICKS_NOTE`: it covers today and tomorrow, leaves next weekend to the weekend briefing, and gives a running festival a nod, not the lead), the `pickTag` row tag (`[ROB'S PICK: reason]` / `[ROB'S PICK]`) and a `formatPicksSection` block. A festival pick hands the model the guide page URL, which `repairEventLinks` leaves alone (it only judges `/events/` links). Lookahead rows come from `getPickRowsBetween` ([lib/briefing-picks-data.ts](../../lib/briefing-picks-data.ts), best-effort: a failed read returns `[]`) and join the `repairEventLinks` set, or a correctly copied mark-your-calendar link would be unlinked. Backstop is log-only: `BRIEFING_PICK_MISSING [where]` when the saved text never links an in-window pick (daily: `mustLink`, today's and tomorrow's picks only, and a festival only on its opening day or the day before). One deliberate difference from the homepage: a guide absorbs only picks dated inside its own run (the homepage's `selectPicks` lets a live guide absorb any matching row), and only when the guide overlaps the surface's window or lookahead, and eligible picks are deduped (after the eligibility check, so a non-pick twin can't win) and tagged by name+date+town+start time (`pickKey`), so a sold-out matinee can't hide or tag the evening show; `pickTag` also checks the row itself, and same-day picks are ordered festival, reason, start time, name so capped lookahead slots are deterministic. Known gap: newsletter lookahead links are not click-tracked (the send route's slug-to-id map covers the 10-day feed only), tracked in #358. Locked by `scripts/test/briefing-picks.test.ts`.
