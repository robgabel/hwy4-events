## First-party engagement tracking (Gate 0)

Cloudflare RUM can't answer the two questions `BUSINESS-PLAN.md` calls Gate 0: **visitor vs local**, and **business-referral clicks**. A lightweight first-party beacon fills the gap (shipped 2026-06-08).

- **`site_events`** (migration `20260608_gate0_site_events.sql`) — one row per page view or outbound business click. RLS on, **service-role only** (no public read). Written exclusively by `/api/track`.
- **`/api/track`** ([app/api/track/route.ts](../../app/api/track/route.ts)) — best-effort POST, never errors to the client (mirrors `/api/track-share`). Classifies **visitor vs local** server-side from Vercel's `x-vercel-ip-*` geo headers via [lib/geo.ts](../../lib/geo.ts) (`classifyVisitor` — a generous corridor bounding box + city-name match; **directional**, since rural IP geo often places locals in a regional hub). UA-flags obvious bots; non-JS bots never fire the beacon at all.
- **Client beacons** ([lib/track.ts](../../lib/track.ts), `navigator.sendBeacon`): `PageViewTracker` (mounted in `app/layout.tsx`) fires one geo-classified view per session+path, skipping `/admin`; `OutboundTracker` (mounted on the event detail page) is a delegated click listener that fires on any `a[data-otrack]` — the source CTA (`more_info`, whether the durable "Visit …" button or the non-durable "Listed on …" line), Get Directions (`directions`), Add to calendar (`add_to_calendar`), Download poster (`download_poster`), Suggest a fix (`suggest_fix`), and a venue's website/phone/maps (data attributes live in `app/events/[slug]/page.tsx`, `components/VenueInfo.tsx`, `components/DirectionsLink.tsx`).
- **Four classes, and the hub is the honest one (2026-09-04).** `visitor_class` ∈ `local | hub | visitor | unknown` ([lib/geo.ts](../../lib/geo.ts) `classifyVisitor`, locked by `scripts/test/geo.test.ts`). Rural ISPs route many corridor residents through a regional hub city (verified 2026-09-04: a Comcast connection in Arnold resolves to **Lodi**), and a hub IP is a mix of hub-routed locals and genuine Central Valley visitors that nothing in the IP can split, so `hub` (an in-state IP city in the region's `geo.hubIpCities`; Calaveras = Sacramento, Stockton, Lodi, Modesto, Sonora) is counted **apart from both** and sits outside every share ratio, never folded into either side. The hub check runs before the bounding box (Sonora sits inside the box but still carries the hub's coordinates). `geo.localIpCities` was widened to the rest of Calaveras County at the same time: Valley Springs alone had 299 sessions since June labeled `visitor`, against 329 labeled `local` in total. Both lists are **region config** (`regions/<slug>/core.ts`; `hubIpCities` is optional, see [docs/REGIONS.md](../REGIONS.md)), never hardcoded in the engine. Migration `20260904_visitor_class_hub.sql` widens the CHECK on `site_events.visitor_class` + `newsletter_subscribers.visitor_class` and teaches the three RPCs (`gate0_stats`, `growth_session_stats`, `growth_outbound_stats`) to count `hub`; **apply it before the code deploys**, because `/api/track` swallows insert errors (a hub row would silently vanish) and `/api/newsletter/subscribe` would 500 on a hub-city signup. Existing rows are **not** backfilled silently: `cd scripts && npx tsx reclassify-visitor-class.ts` (dry-run; `--apply` to write) recomputes the class from the stored city/region for rows since 2026-06-08 and prints before/after counts. It never demotes a stored `local` to `visitor` (a box-only local such as Pioneer has no coordinates on the row to re-derive from); the only moves are `visitor → local/hub` and `local → hub` (Sonora). Tracy (230 sessions) and Elk Grove (193) run high per capita but are deliberately not hubs yet; adding one is a one-line config change.
- **Read-out:** the `/admin/analytics` **Growth** tab shows the local / hub / visitor split (share ratios are over the callable local + visitor sessions, hub excluded) and business-referral clicks (by type + top events) over the tab's selected date range, all labeled directional. The growth memo's signal pack carries `audience.hub_sessions_7d` + `referrals.hub_share_30d` and its prompt is told never to add hub to either side. No new env vars (uses the existing service-role key + automatic Vercel geo headers).

## Search Console (SEO analytics)

Google Search Console is the top-of-funnel demand signal (what people search to reach us — the visitor-acquisition channel, Miguel in BUSINESS-PLAN). Wired live 2026-07-05. Same two-layer shape as the rest of the cockpit: a dumb collector writes rows, a pure lib shapes insight, and two consumers (a human panel + the Growth Agent) read it.

- **Auth (service account, no OAuth):** `lib/agent/gsc.ts` signs a service-account JWT with Node's built-in crypto (zero deps), exchanges it for a `webmasters.readonly` token, and queries the Search Analytics API. SA = `gsc-reader@hwy4events.iam.gserviceaccount.com` (project `hwy4events`), added as a **Full** user on `sc-domain:hwy4events.com`. Key: `~/.config/hwy4/gsc-reader.json` locally + `GOOGLE_SEARCH_CONSOLE_SA_JSON` in Vercel (see Environment Variables). Site defaults to `sc-domain:hwy4events.com` (`GOOGLE_SEARCH_CONSOLE_SITE_URL` to override). `fetchGscCuts(windowDays, historyDays)` returns three cuts (date / query / page), null when the env is unset.
- **Collector:** `/api/agent/collect-seo` (daily 11:00 UTC) writes `seo_snapshots`. New columns (migration `20260705_seo_snapshots_enrich.sql`): `dimension` (`date | query | page | query_page` legacy) + `data_date`. The **by-date** cut is the durable trend spine, **upserted** on a plain `UNIQUE(source, data_date)` (NOT partial — PostgREST `onConflict` can't name a partial predicate; query/page rows carry `data_date = NULL` and Postgres treats NULLs as distinct, so they never collide). by-query / by-page are point-in-time inserts read at their latest `captured_at`. Service-role only (RLS unchanged). Backfill via `?history=480` (the route's own knob — no separate script).
- **Insight (pure, tested):** `lib/seo-insights.ts` — `selectStrikingDistance` (page-1/2 fringe, position ~4–20 with impressions, ranked by un-captured impressions), `monthOverMonth` (last 28d vs prior 28d, split by count so GSC gaps don't skew), `snapshotTotals`. Locked by `scripts/test/seo-insights.test.ts`. `lib/seo-data.ts` `getSeoOverview(supabase)` reads the three cuts (each bounded < 1,000 rows, so no PostgREST truncation) and returns the shaped `SeoOverview` both consumers use.
- **Consumer 1 — human panel:** `/admin/analytics` **Search (Google)** group (28d totals with MoM deltas, striking-distance list, top queries, top pages, clicks-per-day trend). Ordered striking-distance-first (the highest-leverage work).
- **Consumer 2 — Growth Agent:** `lib/agent/growth-context.ts` feeds the memo's `seo` signal (totals + MoM + top + striking); the growth-memo prompt treats the top striking query as a prime move-of-the-week and drafts the specific page change. The chief-of-staff digest reads the latest by-query snapshot (filtered `dimension='query'`).
