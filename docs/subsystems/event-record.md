## Scraped description hygiene (reseller junk)

Concert listings that reach us through ticket-reseller pages arrive with junk a calendar-widget stripper was never built to see. All three shapes shipped live on Ironstone shows and were hand-cleaned once (2026-07-16) before coming straight back on the next scrape, which is why the fix lives in the shared sanitizer rather than in a curator's afternoon (HWY-11, 2026-07-27).

**The scrub runs inside `sanitizeDescriptionDetailed`** ([lib/description-quality.ts](../../lib/description-quality.ts)), so it covers **both** the write boundary (`normalizeEventLocation` in `scripts/lib/dedup.ts`, the hook every `upsertEvents` source calls) and every render path (`displayDescription` / `gateEventDescription`). A stored row therefore stops showing junk on the next revalidation, without waiting for a re-scrape or a backfill. Four passes, in order:

1. **Markdown artifacts** the extractor left literal, usually wrapped around a keyword-stuffed phrase (`This is **Gene Simmons - Murphys Murphys**`). `**`/`__` must wrap real content on one line, so a stray asterisk (a footnote marker, `free* (*with a paying adult)`) survives.
2. **Fake-local venue appositive** — `in Murphys, a local favorite for live entertainment`, `at Ironstone Vineyards-one of the area's go-to spots`. A voice violation as much as a quality one: the neighbor voice is ours and it is earned (`content/VOICE.md`). Deliberately narrow — the phrase alone is not the problem, the **appositive** is, so it must hang off a comma or dash and run to the end of its sentence. The delimiter set **excludes `:`** because the Rotary listing's "Live Music: Local favorites The Fabulous Off Brothers" would otherwise be eaten. Verified against every live row a naive phrase match would hit (the farmers market's "shopping your favorite local vendors", the craft fair's "one of our favorite events of the year"): none match.
3. **Doubled town name** (`Murphys Murphys`). Scoped to the event's **own town**, not any doubled word: genuine reduplicated place names exist (Walla Walla, and this is wine country), so a blanket rule would eventually eat a real one. `sanitizeDescription(text, { town })` — callers without a town simply skip this pass.
4. **Ticket-resale links** (`TICKET_RESALE_HOSTS`) are stripped outright, along with the dangling "Tickets at ." they leave behind. A reader following one can only be overcharged for a show whose venue sells directly (regtixs.com was the live case).

**The link rule is a denylist, not the allowlist it looks like it should be.** Checked against live data first: all 22 URLs then sitting in upcoming descriptions were legitimate — organizer sites (murphyscreektheatre.org, angelsmurphysrotary.org) and real sellers (ticketleap.com, onecau.se) — and an allowlist would have deleted every one, since the sanitizer is a pure function with no view of the org/venue registry. Stripping good links to catch bad ones is the worse trade. The whack-a-mole gap is closed by **flagging** instead: `findSuspectTicketLinks` ([lib/audit-checks.ts](../../lib/audit-checks.ts)) reports a daily `suspect_ticket_links` count for any *ticket-selling* URL whose host is neither a known reseller nor in `KNOWN_TICKET_HOSTS`. A human then adds the host to whichever list it belongs in. Plain organizer links are not ticket-ish and stay quiet.

Locked by `scripts/test/description-quality.test.ts` and `scripts/test/audit-checks.test.ts`, both of which assert what must **survive** as hard as what gets removed. Ship-time dry run over every distinct at-risk live description: 1 changed (the junk row), 7 byte-identical.

**Concrete-value override (HWY-46).** `assessDescription` still flags stubs (`too_short` under 15 words, `no_terminal_punctuation`, `generic_hype`), but a price, a comma-separated lineup/menu/activity list (≥2 short items), or a proper noun moves the verdict from suppress to pass/rewrite. A name that is also in the title counts ("Miss Debbie"); venue, town, and month names do not, so "runs June 13–14" at Bear Valley stays suppressed. A clock time or a lone hint word ("family") does not override a stub: "Bingo. Doors open 5:30pm" and an unpunctuated "family activities…" sentence stay hidden. `empty` and `ends_with_colon` stay hard suppressors. Render-only; stored descriptions are not rewritten.

## Event Pricing (cost_tier)

Some events charge admission (Brice Station concerts, ticketed festivals). The fee is often present in the scraped `price` free-text or buried in the description, but free-text can't drive a badge or filter — so we derive a typed signal.

- `hwy4_events.price` — human-readable amount string (`"$25"`, `"Pay what you can"`). Unchanged.
- `hwy4_events.cost_tier` — typed enum: `free | paid | donation | varies | unknown`. The handle the UI keys off.
- `hwy4_events.price_extracted_at` — when `/api/extract-prices` last processed the row (NULL = queue candidate).
- `hwy4_events.price_locked` — manual override (mirrors `importance_override`). When `true`, `price` + `cost_tier` are human-set and **no automated writer touches them**: `/api/extract-prices` skips locked rows, and the scraper (`scripts/lib/dedup.ts`) omits `price` from every update payload (exact-match, fuzzy-merge, serial + batched paths).
- `hwy4_events.description_locked` — sibling to `price_locked` for the free-text `description`. When `true`, the scraper (`scripts/lib/dedup.ts`) omits `description` from every update payload, so a hand-edited description survives re-scrapes.
- `hwy4_events.poster_locked` — sibling to `price_locked` / `description_locked` for `image_url`. When `true`, the image is human-pinned (curator found a great poster) and the scraper omits `image_url` from every update payload (exact-match, fuzzy-merge, serial + batched paths). Use when a scraped or manually-found image is exactly right and must not be overwritten. Set via SQL: `UPDATE hwy4_events SET image_url='...', poster_locked=true WHERE id='...'`. To lock without changing the image: `UPDATE hwy4_events SET poster_locked=true WHERE id='...'`. Same caveat as `price_locked`: new rows for recurring events start unlocked. Use when the source's prose carries something stale that re-scrapes keep restoring — e.g. Ironstone "Mimosa Sundays", whose GoCalaveras description literally says "$15 each". Set via SQL: `UPDATE hwy4_events SET description=…, description_locked=true WHERE …`. Same per-row caveat as `price_locked`: new rows for a recurring event start unlocked. Use this when a source's listed price is wrong or stale and re-scrapes/extraction would otherwise keep restoring it — e.g. Ironstone "Mimosa Sundays", whose description literally says "$15 each" so extract-prices re-lifted $15 every run. Set via SQL: `UPDATE hwy4_events SET price=…, cost_tier=…, price_locked=true WHERE …`. **Caveat:** the lock is per-row. A recurring weekly event keeps getting *new* rows inserted for future dates; those start unlocked, so a stale price can reappear on the newly-scraped Sundays and they need re-locking (re-run the same UPDATE periodically).
- `hwy4_events.sold_out` — human-set "tickets are gone" marker (migration `20260903_add_sold_out.sql`, default false). A sold-out event is still a real event, so it stays in every feed, keeps its detail page, and keeps its JSON-LD (the offer's `availability` flips to `schema.org/SoldOut` in `lib/schema.tsx`); what changes is that it stops being a *recommendation*. It renders a loud `bg-alert` **SOLD OUT** badge leading the badge row on both the card ([components/EventCard.tsx](../../components/EventCard.tsx)) and the detail page, and `selectPicks` ([lib/picks.ts](../../lib/picks.ts)) drops it from the homepage spotlight/Rob's Picks row even if `robs_pick` is still true (belt-and-braces: clear either one and it falls out). **No automated writer touches the column** — every scraper payload in `scripts/lib/dedup.ts` enumerates its columns explicitly, so nothing can clear it, which is why it needs no `*_locked` sibling. Set via SQL: `UPDATE hwy4_events SET sold_out=true, robs_pick=false WHERE id=…`; reverse by setting it back to false. Same per-row caveat as the locks: new rows for a recurring event start unsold. **Currently unused:** it was built for the "Meet Me in Murphys Summer Concert" (2026-09-05), which the organizer then pulled from listings entirely (that row is `status='cancelled'`), so no row carries the flag today and the badge renders nowhere. The column is applied in prod and inert; the next sold-out event is one UPDATE away.
- `hwy4_events.times_locked` — sibling to `price_locked` / `description_locked` / `poster_locked` for `start_time` + `end_time` (migration `20260725_add_times_locked.sql`). When `true`, the times are authoritative (human-set, or applied from the organizer's own canonical page) and **no automated writer touches them**: `scripts/lib/dedup.ts` omits both columns from every update payload (exact-match, fuzzy-merge, serial + batched), `rowChanged` stops counting a time diff as a change, and the self-contained `/api/scrape-moose-lodge` route strips them too. Added 2026-07-25: the Arnold Rim Trail sunset hikes were 30 minutes wrong on the day of the hike because the organizer moves the time as sunset shifts while our aggregator-sourced row was frozen at the April scrape — and there was previously **no way to pin a corrected time**, since every scraper wrote `start_time` unconditionally. Set via SQL: `UPDATE hwy4_events SET start_time=…, end_time=…, times_locked=true WHERE id=…`; unlock with `times_locked=false`. Same per-row caveat as the others: new rows for a recurring event start unlocked. Locked by `scripts/test/times-locked.test.ts`.
- `hwy4_events.visibility_locked` — sibling to the other locks for `visibility` (migration `20260905_add_visibility_locked.sql`, HWY-24). When `true`, the public/members-only setting is human-set and no automated writer touches it. Added 2026-09-05 after two members-only Moose Lodge gatherings (a members' dinner, a volunteer work call) were found live on the **public** site: `/api/scrape-moose-lodge` reads a PDF with an LLM, so `visibility` is a model verdict **re-derived every Monday**, and a hand-correction was guaranteed to be overwritten. This is a privacy-shaped defect, not a cosmetic one. **Note the shared path was never the exposure:** `scripts/lib/dedup.ts` writes `visibility` on INSERT only, so no `upsertEvents` scraper can flip an existing row; `scripts/test/visibility-locked.test.ts` pins that too, so a future "self-heal visibility" edit to a payload builder can't quietly open the hole. The window-scoped stale sweep treats `visibility_locked` as a protected row (`isProtectedRow` in `scripts/lib/stale-sweep.ts`, HWY-49), so a human-pinned listing is left in place when it drops off the source calendar instead of being archived. Set via SQL: `UPDATE hwy4_events SET visibility='private', visibility_locked=true WHERE id=…`; unlock with `visibility_locked=false`. Same per-row caveat as the others. **Same pass also fixed that route ignoring `description_locked`/`price_locked`** (it writes both fields, so a hand-corrected description or price reverted every Monday) **and re-asserting `robs_pick`/`is_weekly` on update**, which would clear a curator's Rob's Pick.
- `hwy4_events.family_friendly` / `family_friendly_locked` — stored Kids-chip tag (migration `20260911_add_family_friendly.sql`, HWY-34). Scrapers stamp `family_friendly` from `resolveFamilyFriendly` on INSERT and on unlocked UPDATE; when `family_friendly_locked` is true no automated writer touches the flag. There is no event-edit UI — set via SQL: `UPDATE hwy4_events SET family_friendly=true, family_friendly_locked=true WHERE id=…`; unlock with `family_friendly_locked=false`. A `qa_fix_event` proposal can toggle the flag and refuses when the lock is already set. Approving the fix sets `family_friendly_locked` in the same update (and the matching `*_locked` flag for every other guarded column) so the next scrape cannot revert the value. Revert clears only the locks that approval turned on. Same per-row caveat as the others. See the Kids quick-filter bullet above. Locked by `scripts/test/family-friendly.test.ts` + `family-friendly-locked.test.ts`.
- **Lock-consumer registry ([lib/lock-consumers.ts](../../lib/lock-consumers.ts), HWY-50).** The seven `hwy4_events.*_locked` columns are read by six consumers that legitimately check different subsets: QA fix (`LOCK_GUARDS` / `ACKNOWLEDGED_UNGUARDED_LOCKS`), stale sweep (`STALE_SWEEP_LOCK_GUARDS`, which `isProtectedRow` reads — including `visibility_locked`, HWY-49), the dedup update path, `/api/scrape-moose-lodge`, insert-only `/api/scrape-bls`, and `cancel_event` (`CANCEL_EVENT_LOCK_ACKS`: the approval sets `status='cancelled'` and acknowledges every lock because it does not write that column). Each consumer declares, per lock, the field it guards or a one-line acknowledgement. `findLockConsumerDrift` fails when a live `*_locked` column has no stance on a registered consumer. CI pins the registry against repo SQL in `scripts/test/lock-consumers.test.ts` (and against the guarding source, same shape as `scraper-venue-literals`); the daily `qa-schema-drift` Action runs the same check on the live table. Do not collapse the six declarations into one shared lock list.
- `/api/extract-prices` runs daily; reads description+name and lifts **explicitly-stated** fees via Haiku. Never guesses an amount — no fee text means `cost_tier='unknown'`, not free. Skips `price_locked=true` rows.
- The public site shows a green **"Free"** badge or a **"$25" / "Ticketed" / "Pay what you can"** cost badge on each event card (scan-level), plus a **"Free"** quick filter on the homepage. `unknown` shows nothing.
- Backfill the whole upcoming queue by hitting the route repeatedly (it's idempotent via `price_extracted_at`): `curl -H "Authorization: Bearer $CRON_SECRET" "https://hwy4events.com/api/extract-prices?limit=150"`.

## Outbound Event Links

The "Visit Event Page" button links to a **destination derived from event identity, not scrape provenance**. See `PRD-event-link-resolution.md`.

**Priority order (first hit wins):** organizer canonical → venue canonical → stable-source `event_url` → GoCalaveras fallback → none (community / no source).

The Visit button is still that destination. A separate **Source** line on every event page names where the listing was found (`resolveSourceReceipt` in [lib/source-receipt.ts](../../lib/source-receipt.ts)). The two can disagree: Visit may open a venue site while Source opens the dated GoCalaveras or Visit Murphys page.

- **Source receipt (#400, 2026-10-14).** Every detail page, including the parade layout, renders `Source: {label} (seen {last_scraped_at})` from `resolveSourceReceipt`. It links `event_url` (GoCalaveras, Visit Murphys, Facebook, an organizer permalink) even when Visit points at a venue homepage or an organizer calendar. With no external `event_url`, an external `source_url` (calendar page or PDF) wins over a stored photo and links under the source name (Moose Lodge, Murphys Irish Pub). "submitted flyer" is only a `community_sourced` image. A scraped photo with no external source links the image under the source name. A community row with neither says "Submitted by community" and is not a link. `https://hwy4events.com/submit` is not a receipt. `last_scraped_at` is read on the detail query (`EVENT_COLUMNS`). No new column. Visit ranking is unchanged (#362). Locked by `scripts/test/source-receipt.test.ts`.
- **`lib/event-link.ts`** is the single source of truth for the Visit button: `resolveEventLink(event, { org, venueUrl })` resolves in the priority order above. `matchOrgForEvent(event, orgs)` maps an event to its organizer by `org_slug` (only when that org has a `canonical_url` — an aggregator slug like `gocalaveras` deliberately falls through) or by `hwy4_orgs.match_patterns` (normalized substring; enumerate spelling variants — the source really lists "Aronld Rim Trail"). Locked by `scripts/test/event-link.test.ts`.
- **Venue canonical (priority #2) is `hwy4_venues.website`, gated by `promotableVenueUrl(venueName, website)`** (2026-06-06 — the path existed since 2026-05-30 but was never fed any data; it was dead code until the detail page started passing `venueUrl`). A venue website only promotes to a durable CTA for **single-operator** venues: `isMultiTenantVenue()` rejects parks / community centers / town squares / fairgrounds / amphitheaters (no single events page exists, and the auto-matched Places website is often a generic homepage or a flat-wrong match — Perry Walther Community Center matched a Bear Valley parents group), and social-page websites (Facebook/Instagram/X) are rejected too, as are **aggregator/unstable-host** websites (Google Places sometimes syncs a GoCalaveras listing in as a venue's "website" — e.g. Angels Camp Museum — and a non-durable host is never a durable destination). So e.g. Stevenot Winery + Murphys Wine & Beer Garden events resolve to the venue site; a Murphys Community Park event keeps the GoCalaveras fallback. Both helpers are shared by the detail page and the `/api/check-events` audit so the page and the KPI can't disagree. Promotion needs the event's `venue_key` populated (no key → no venue lookup → falls through to the source/fallback).
- **Social hosts are never durable (2026-09-05).** `isUnstableHost` now returns true for `facebook.com` / `instagram.com` / `twitter.com` / `x.com` as well as the region's aggregators, so a Facebook event permalink stays out of the Visit button and out of JSON-LD `offer.url` (the Source line still links it) and out of `validateEventUrls`. This **reversed** a deliberate prior decision (two tests asserted `durable: true`), and the argument that justified it did not change — a Facebook *page* is not event-specific, but an event *permalink* is. The **stakes** changed: `hwy4-fb-pages` merges FB permalinks onto rows routinely, where before the whole catalog held four from a one-off run, so "durable" would start feeding facebook.com into schema.org offers as a matter of course — against the site's own thesis of being the canonical answer. The set is hardcoded in `lib/event-link.ts`, **not** region data: `unstableSourceHosts` lists the region's aggregators (GoCalaveras is a Calaveras business), while Facebook is the same everywhere and a 30A deployment must inherit it rather than remember to re-list it. `promotableVenueUrl`'s own social check is now redundant and delegates to the shared gate.
- **`UNSTABLE_SOURCE_HOSTS`** (currently `gocalaveras.com`) are aggregators whose per-event links 403 server-side validators but return 200 in a real browser. **`AGGREGATOR_FALLBACK`** (`true` as of 2026-06-03): a GoCalaveras event with no organizer/venue match renders that GoCalaveras link as a **non-durable** (`durable:false`) source. **The detail page scales source prominence to durability** (2026-06-21): a durable organizer/venue/stable-source link gets a high-contrast outline **"Visit … ↗"** button in the action rail (the conversion CTA), while the Source line (not a second button) names the listing we read — source *presence* is universal (credibility + an accuracy safety valve so a reader can verify if our data is wrong), but only durable links earn button weight. Share stays the sole filled primary (the only growth loop); on mobile the Visit button is a secondary outline, never co-equal. Community submissions are excluded. The link is **kept out of JSON-LD** (`offer.url` always uses our own stable event page when `durable:false`) so a potentially-churnable permalink never leaks into structured data. **Defense in depth (2026-06-21): an unstable host is never durable in ANY slot.** A misconfigured `hwy4_orgs.canonical_url` or `hwy4_venues.website` that is *itself* a GoCalaveras URL can't launder a churnable link into a durable CTA (or into JSON-LD): `resolveEventLink`'s organizer branch skips a canonical whose host `isUnstableHost`, and `promotableVenueUrl` rejects an unstable venue website. Real cases caught: the `the-stitch-lounge` org row (canonical was a GoCalaveras permalink) and the `angels-camp-museum` venue (Places-synced GoCalaveras "website") — both now resolve to `null`/non-durable. Locked by `scripts/test/event-link.test.ts`. Both rows were also cleaned in the DB (2026-06-21: org `canonical_url` nulled; venue `website` nulled + `places_locked`). **Write-time guard too:** `/api/sync-venue-facts` drops an `isUnstableHost` website on every sync (`website: details.websiteUri && !isUnstableHost(...) ? ... : null`), so Google Places can't re-store a GoCalaveras "website" on any venue — the stored data stays clean, not just the read path.
- **Consumers of the Visit button** (all import the resolver; the Source receipt is the one reader of `event_url` as provenance): the event detail CTA + its JSON-LD `offer.url` ([app/events/[slug]/page.tsx](app/events/[slug]/page.tsx)), the patriotic detail layout, and `buildEvent` in [lib/schema.tsx](../../lib/schema.tsx) (which points `ItemList` offers at the internal page). **The event cards** ([components/EventCard.tsx](../../components/EventCard.tsx)) deliberately render **no** outbound/provenance line (2026-06-22): a card's whole surface links to our own richer detail page, and source attribution ("Listed on GoCalaveras", durable "Visit …" buttons) lives there — duplicating it on every card added noise and leaked clicks off-site. The server-side `outboundLink` list-field was **removed 2026-07-01** (it had been computed on every cached row since 6/22 but rendered nowhere; its two per-cache-window context queries — `hwy4_orgs` + `hwy4_venues` — went with it). If a card ever needs an outbound link again, resurrect `buildOutboundLink`/`loadLinkContext` from git history. The three briefing/newsletter generators already link to internal pages, so they were always safe.
- **To give an organizer's events a durable link**, add the org to `hwy4_orgs` with `canonical_url` + `match_patterns` (no code change). That upgrades the event from the GoCalaveras fallback to the organizer's own site. `/api/verify-events` shares the same `matchOrgForEvent`, so date-verification and link resolution always agree on which org owns an event.
- **`validateEventUrls`** ([scripts/lib/validate-urls.ts](../../scripts/lib/validate-urls.ts)) skips `UNSTABLE_SOURCE_HOSTS` (a 403 from our server is not a dead user-facing link), checks upcoming events only, and nulls a link only on a GET-confirmed 404/410 (see "URL validation" under the Red Cross source).
- **`/api/check-events` link-gap KPI.** The audit reports two things: `aggregator_fallback_links` (raw count of events whose best link is only the non-durable GoCalaveras fallback — trend signal) and `actionable_link_gaps` — **single-operator** venues with **≥5 upcoming events** using only the fallback (`GAP_VENUE_THRESHOLD` in the route). The audit applies the same `promotableVenueUrl` guard as the page (so venues that already resolve to a durable venue link drop off) and excludes `isMultiTenantVenue` parks/community-centers/town-squares from the actionable list (those have no single canonical events page — the fallback is their correct terminal state, so they're not "go add an org row" work; they still count in the raw trend number). Net: the worklist surfaces only genuine single-operator organizers (a new concert series, a winery, a bar) worth a ~10-min `hwy4_orgs` row. Watch `actionable_link_gaps`, not the raw count.
- **Decision (2026-05-30): do NOT build canonical auto-discovery.** The long tail is one-offs where the GoCalaveras fallback is correct. Only revisit if `actionable_link_gaps` climbs fast. To give an organizer a durable link, add its `hwy4_orgs` row by hand (canonical URL must be a page that renders server-side — JS-only calendars like `bigtrees.org/events/` are fine as a *link* but can't be enrolled in `canonical_check_enabled` date-verification).
