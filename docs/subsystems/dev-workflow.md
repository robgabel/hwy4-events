## Dev Workflow

- **PR workflow (standing rule, 2026-09-24):** branch from a fresh `origin/main`, open a draft PR, then a separate subagent QAs it per [.claude/skills/pr-qa/SKILL.md](../../.claude/skills/pr-qa/SKILL.md). Any finding goes to Rob as three options plus one recommendation and the builder waits for his pick; fix, re-QA until PASS. Rob merges, never Claude, never auto-merge.
- `npm run dev` for local development
- Vercel auto-deploys from `main`
- Migrations in `supabase/migrations/` — apply via Supabase dashboard or CLI
- **Scripts typecheck root resolves `@/` (HWY-75, 2026-10-04).** `scripts/tsconfig.json` maps `@/*` to `../*`, the same alias the root tsconfig maps to `./*`. The scripts root type-checks every root `lib/` file a scripts test reaches, and 14 `lib/` files import through the alias, so without the mapping the first test to import one of them turns the root red for an import nobody changed (the first was `scripts/test/expire-submissions.test.ts` reaching `lib/agent/submission-reply.ts` via #302). Keep the two mappings pointing at the same directory.
- **Tests:** `cd scripts && npm test` (Node's built-in test runner + tsx, zero extra deps) — pure-logic locks in `scripts/test/*.test.ts` (dedup/event-identity, sitemap, voice lint, inbound-email, venue-gaps, weather, etc.). CI runs them on every PR touching `app/`, `content/`, `lib/`, or `scripts/` via [.github/workflows/test.yml](../../.github/workflows/test.yml), which installs **both** root and `scripts/` deps — the scripts tests import root `lib/` modules, some of which import app deps like react (so a scripts-only install fails in CI with "Cannot find module 'react'", even though it passes locally where the worktree is nested inside the app's node_modules). The same workflow's **`typecheck` job** runs `npx tsc --noEmit` at the repo root **and** `cd scripts && npx tsc --noEmit` (root `tsconfig.json` excludes `scripts/`, so one `tsc` cannot cover both trees).
- **Venue & address resolution:** `scripts/lib/venues.ts` is the venue registry (canonical name, aliases, town, street address) — the single source of truth. The matcher (`scripts/lib/venue-matcher.ts` `applyVenueDetection`) resolves generic/messy venue names; the upsert path (`scripts/lib/dedup.ts` `normalizeEventLocation`) fills a registry address when an event's address is missing or town-only, and when a source puts a street address in the venue-NAME field (EventON does), the swap re-runs detection gated to the ADDRESS layer only — an address matching a registry venue adopts its canonical name and town, while a venue merely mentioned in title/description/URL text never does (2026-08-19, the Arnold Angels red runs; the town adoption is what un-reds the location sanity check). When a real venue shows up with a bad/missing address, add it to the registry — don't hand-edit rows. A venue with more than one street address lists the extras in `addresses` (matching only; `address` stays the display address), e.g. the fairgrounds' 2465 Gun Club Rd gate beside 101 Frogtown Rd (dedup v2 Phase 0.2); the ambiguity filter still drops any address two venues share. To retro-fix existing rows after a registry change, run `cd scripts && npm run backfill-venues` (dry-run; add `--apply` to write, `--future-only` to limit). Out-of-corridor venues are dropped at write time via `scripts/lib/corridor.ts`. The daily `/api/check-events` audit reports any remaining unresolved venues / town-only addresses to Slack. **A venue fact hardcoded in a raw-insert writer is pinned to the registry by `scripts/test/scraper-venue-literals.test.ts` (HWY-25, 2026-09-05).** `/api/scrape-moose-lodge`, `/api/scrape-bls` and `scripts/scrapers/bistro-espresso.ts` write their own INSERT, so they never get `normalizeEventLocation`'s registry address fill and each keeps a second copy of a fact `venues.ts` owns — which is how the lodge shipped 18 rows at `3049 CA-4` when it is on Blagen Rd (wrong map thumbnail, wrong Get Directions; corrected in #249, but nothing stopped it drifting again). The test is the `image-hosts.test.ts` pattern: the duplicate may exist, but CI fails the moment it stops matching. It also pins **venue NAMES to registry canonicals**, which caught a live second instance: `scrape-bls`'s `resolveVenue` returned the alias spellings `"BLS Amphitheater"`/`"BLS Pool"`, and since that route raw-inserts, those strings landed in `venue_name` verbatim and could never resolve to a `venue_key` (no hub page, no Places facts, no address). Its fourth name, `"Blue Lake Bistro"`, was in no registry entry at all and is now registered beside its Snowflake Lodge complex siblings.
- **Static venue maps:** the event detail page shows a static map thumbnail centered on the **venue** (not the town) and only loads the interactive Leaflet map on tap. The page server-geocodes the address ([lib/geocode.ts](../../lib/geocode.ts), cached weekly, tag `geocode`) and renders `<img src="/api/static-map?lat&lng&z">`. That route ([app/api/static-map/route.ts](../../app/api/static-map/route.ts) + [lib/static-map.ts](../../lib/static-map.ts)) stitches CARTO Voyager tiles with `sharp` into a webp, cached **immutably** (the image is a pure function of lat/lng/zoom + `BASEMAP_VERSION` — bump that version, never bust the URL). Tiles need `NEXT_PUBLIC_CARTO_API_KEY` (see Environment Variables) or they arrive watermarked. No street address / geocode miss → falls back to the town centroid. The old pre-baked `public/maps/*.webp` town assets and `generate-town-maps.ts` were removed in favor of this.
  - **Warm + bust:** after a deploy or a venue/address backfill, run `cd scripts && SITE_URL=https://hwy4events.com REVALIDATION_SECRET=… npm run warm-maps`. It busts the `geocode` tag via `/api/revalidate` (so pages re-geocode with corrected addresses) and pre-warms `/api/static-map` for every distinct upcoming-event center. `REVALIDATION_SECRET` lives in Vercel env, not local `.env.local` — set it inline to enable the bust (warm runs without it).
