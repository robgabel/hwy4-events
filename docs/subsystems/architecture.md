## Architecture

- Events are scraped externally and loaded into Supabase — this app is **read-only** against event data (except community submissions via `/submit`)
- Community submissions land in `event_submissions` (status `pending`). Review and publish them at **`/admin/submissions`** (see `PRD-admin-submissions.md`): **Publish** inserts a `community_sourced` `hwy4_events` row (`source_name='Community Submission'`, `visibility='public'`, `status='confirmed'`, a `dedup_key` from the shared `generateDedupKey` in `lib/event-identity.ts`) and flips the submission to `approved` (recording `published_event_id`); **Dismiss** sets it `rejected`. `community_sourced=true` renders a pine **"Community sourced"** badge on the event card and detail page. **The publish path runs the shared write-time machinery (2026-07-28).** It used to raw-insert the reviewer's form fields, making it the one writer that skipped everything `upsertEvents` does for a scraper: no venue resolution (so a community row entered with `venue_key IS NULL` and no address, stripped of the strongest dedup signal there is) and no duplicate check beyond the `dedup_key` unique index, which only catches a byte-identical re-listing. Now `publishSubmission` (a) resolves the venue against `hwy4_venues` via `matchVenueRow` ([lib/venue-match.ts](../../lib/venue-match.ts), the app-side registry lookup — `tsconfig.json` excludes `scripts/`, so the scraper's matcher can't be imported; an ambiguous name resolves to null rather than guessing a key that would assert a shared room) and stamps `venue_key` + the registry address, and (b) **refuses to publish a row the shared `isSameEvent` reads as an event already listed**, naming it and pointing at Merge. The block is overridable by a "Publish anyway" checkbox, because the matcher is a heuristic and the reviewer is the authority; what must not happen is publishing a duplicate *silently*.
- **Submission triage (agent advisory, Stage 1 of the Agent Cockpit).** Every new submission is auto-researched by an agent (`lib/agent/submission-triage.ts`): it checks the DB for an existing match with the shared `isSameEvent`/`generateDedupKey` matcher (**corridor-wide**, ±3 days — it was same-town until 2026-07-28, which is precisely why it missed the Doc Nancy duplicates: the submitter's town label and the resident row's disagreed, so the model was handed an empty candidate list and correctly concluded `publish_new` from it; candidates are now ranked exact-key → strong-match → same-town before a 40-row cap, and the prompt tells the model to treat town as a soft label on both sides), then web-searches (Anthropic `web_search_20250305` + Sonnet `claude-sonnet-5`) for the organizer/canonical page, and stores a verdict on the row (`ai_verdict` ∈ `publish_new | duplicate | duplicate_needs_update | reject`, plus `ai_confidence`, `ai_headline`, `ai_matched_event_id`, and a full `ai_analysis` jsonb of rationale / new_info / suggested-field-fills / sources / flags — migration `20260606_submission_triage.sql`). `/admin/submissions` renders a color-coded verdict banner, pre-fills blank publish-form fields from the research, and for `duplicate_needs_update` offers a one-click **Merge** (`mergeSubmission` in `actions.ts`) that fills only blank fields on the matched event (respects `*_locked`), snapshotting the prior row to `event_submissions.merge_snapshot` for reversibility. Triggered three ways: on submit via `after()` in `/api/submit-event`, a daily cron backstop (`/api/agent/triage-submissions`, 18:30 UTC), and a manual "Re-analyze" button. **The agent only advises; a human always clicks Publish/Merge/Dismiss.** The chief-of-staff digest reads these verdicts into `/admin/today`. **Reply loop (CRM):** each decision drafts a short reply to the submitter in the site's neighbor voice (`lib/agent/submission-reply.ts`, stored in `event_submissions.ai_reply`, migration `20260606b_submission_reply.sql`): **approve** → "your event is live" with the link; **"Draft a question"** button → asks only about the exact gaps the triage found; **dismiss with a reason** → a gracious decline (skipped for `possible_spam`). The admin UI shows the draft in an **editable panel** (`components/admin/EditableReplyPanel.tsx`, a client component) — Rob can tweak the subject/body in place and the one-click **Gmail compose deep-link** rebuilds live from the edited text (so the edits land in the pre-filled compose window); "Reset to draft" restores the agent's copy, and edits are page-local (not persisted to `ai_reply`). Those drafts are not sent by the app; Rob edits and sends from his own Gmail (no inbox credentials in the app). The exception is the daily expire job below, which sends its own fixed copy.
- **Email-to-event ingestion** (`PRD-email-ingest.md`) — a **thin front door** on the triage engine above. A curator forwards an event email (often with a poster) to a Resend Inbound address → [`/api/inbound-email`](../../app/api/inbound-email/route.ts) (Svix-signed webhook + sender allowlist `INBOUND_EMAIL_ALLOWLIST`, fails closed). Resend's `email.received` webhook is metadata-only, so the route fetches the body + attachments back (`resend.emails.receiving.get` / `.attachments.list`), reads the email **and** the poster via Sonnet, uploads the flyer to the `event-posters` bucket, and lands a `source='email'` pending `event_submissions` row — then fires the **same `triageSubmissionById`** the form uses. Everything downstream is reused unchanged: the triage verdict, the `/admin/submissions` review (now with an "Email" badge + "Original email" view), the reversible `mergeSubmission`, and publish-pins-the-poster. Idempotent on Resend's `email_id`. Pure core (prompt/parse/normalize/signature) in `lib/inbound-email.ts`, locked by `scripts/test/inbound-email.test.ts`. Columns added: `source`, `poster_url`, `raw_email`, `source_message_id` (migration `20260604b_email_submissions.sql`).
- Weekly recurring events use `is_weekly: true` and get collapsed in the UI (`CollapsedEvent` type)
- **Homepage feed collapse + Highlights toggle ([lib/collapse-events.ts](../../lib/collapse-events.ts), 2026-07-08).** The 60-day homepage window carried ~530 rows of which ~2/3 were instances of ~30 recurring series (Big Trees guided walks 40×, Junior Rangers 35×, weekly storytimes/trivia/maker sessions) wallpapering the same card onto every day-group — the clutter problem. `collapseEventList` (pure, locked by `scripts/test/collapse-events.test.ts`) says each happening once: **runs** (span ≤7 days, or a near-daily median cadence over a longer span — festival nightly rows, weekday camps) become one date-range card (`endDate`/`dayCount`; the old EventList multi-day behavior, preserved), and **spaced weekly-ish series** become their next not-yet-ended occurrence with a data-derived `seriesCadence` chip ("Weekly"/"Repeats") + `seriesCount`. Grouping is base-name + town; clock-aware, so a range card whose remaining days run at different hours (Murphys Homecoming: Friday 7–9 PM kickoff, Saturday 11 AM–5 PM) nulls its times and renders a "Times vary" chip (`timesVary` on `CollapsedEvent`, 2026-07-17) instead of asserting day 1's hours for the whole span; a card re-anchors to its next not-yet-ended instance once today's ends — a series card jumps to next week's date, and a mid-run range card moves under tomorrow ("Jul 15 – Aug 7", dayCount = remaining days) instead of squatting in Today after the day's session is over (the 2026-07-14 11 PM "ended events still showing" fix). Live-data measurement at ship time: 534 rows → 154 cards. On top sits a persisted **Highlights | Everything** segmented toggle in EventList's quick-chip row (two honest stops, deliberately NOT a slider or an LLM score — the DB's `importance`/`importance_score` columns remain unpopulated/dormant; their last live code references — the `Hwy4Event` type fields and the two stray select-list mentions — were deleted 2026-08-11, HWY-19, since nothing ever wrote them): `isHighlightEvent` keeps every distinct happening and drops only the recurring regulars, with `robs_pick`, festivals, and recurring live music with a named act always staying. Default is Everything, so nothing is hidden until the reader chooses. Homepage-only for now (SimpleEventList on town/temporal pages renders uncollapsed rows).
- **Homepage feed shaping ([lib/events-data.ts](../../lib/events-data.ts)).** The shared `getUpcomingEvents` returns the full deduped upcoming set (the temporal pages, town pages, and sitemap all read it). The **homepage** instead calls `getHomepageEvents()`, which bounds the feed to `HOMEPAGE_HORIZON_DAYS` (60) so it doesn't serialize the entire ~1,000-row catalog (dated to 2028, including ~300 weekly-recurrence instances) into the client for filtering; curated `robs_pick` events bypass the cap so a highlight further out is never hidden. Rows then pass through `toListEvents()` → `EventListItem`, a display-only projection (description trimmed to ~280 chars; scrape/audit columns like `address`, `source_event_id`, and the `*_at` timestamps dropped, but `source_name`/`source_url`/`event_url` kept for the card's "via" source link) so only what a card renders crosses the wire. `CollapsedEvent extends EventListItem`, so the type checker guarantees no card reads a dropped field, and the full rows still feed JSON-LD + the detail page. Net: the homepage document went ~1.6MB → ~0.8MB raw (~58% off the brotli wire). Widen/narrow the homepage window with the one `HOMEPAGE_HORIZON_DAYS` constant. **Curation layer:** above the filterable list, [components/RobsPicks.tsx](../../components/RobsPicks.tsx) (server-rendered, no client JS, no images) shows an "If you do one thing this week" spotlight — the soonest public `robs_pick` within 7 days Pacific — plus up to 4 further picks; selection rules live in [lib/picks.ts](../../lib/picks.ts) (`selectPicks`, locked by `scripts/test/picks.test.ts`), and the section renders nothing when no upcoming pick or live guide exists. Selection is **time-aware** (2026-07-05): a pick that has already ended drops via the shared `hasEventEnded` in [lib/event-time.ts](../../lib/event-time.ts), the same predicate the client "Up Next" logic uses (now with a cross-midnight end guard), accurate to the homepage's `revalidate` window (1800s, matching the feed cache). And **guide-aware**: a live `FESTIVAL_GUIDES` entry ([lib/event-guides.ts](../../lib/event-guides.ts), which carries `startDate`/`title`/`town` for this) is a first-class pick entry that renders as a date-range card for the festival's whole run `[startDate, hideAfter]`, links to the guide page, stays spotlighted while in progress (the umbrella event row leaves the upcoming feed after opening day, so it can't carry this), and absorbs any `robs_pick` event row it matches (umbrella or nightly), so the highlight is always the festival page, never one night of it. Next year's festival = one new registry entry; no robs_pick juggling.
- **Kids quick filter as a stored family-friendly tag ([lib/family-friendly.ts](../../lib/family-friendly.ts), HWY-34).** `hwy4_events.category` is single-valued, so a concert that says "kids welcome" stays `live_music` (Mia's Live Music chip) and used to vanish when Jen tapped Kids. Durable columns: **`family_friendly boolean not null default false`** + **`family_friendly_locked`** (same lock family as `price_locked` / `description_locked` / `times_locked` / `poster_locked` / `visibility_locked`). `isFamilyFriendly` is the pure never-guess predicate over name+description (explicit hospitality language promotes; age-gate language — 21+, must be 21, no minors, adults only — vetoes even a "kids welcome" mention). Bare "family"/"kids" is not enough (Willie Nelson & Family, Children's Advocacy Center, "friends, family and supporters"). Write paths stamp `family_friendly` from `resolveFamilyFriendly` (`category==='kids'` OR the predicate) on INSERT and on unlocked UPDATE, from the name+description that will actually be stored. The homepage Kids chip is `category==='kids' OR family_friendly===true` (`matchesKidsFilter`); Event Type checkboxes stay category-pure. No recategorization. There is no event-edit UI for the lock — flip it in SQL (or a `qa_fix_event` proposal, which honors the lock): `UPDATE hwy4_events SET family_friendly=true, family_friendly_locked=true WHERE id=…;` / unlock with `family_friendly_locked=false`. One-time backfill: migration stamps `category='kids'`; `scripts/backfill-family-friendly.ts` (dry-run / `--commit`) applies the JS predicate to unlocked rows. Locked by `scripts/test/family-friendly.test.ts` + `family-friendly-locked.test.ts`.

One config-driven server view ([components/IntentPageView.tsx](../../components/IntentPageView.tsx), the TemporalEventsView sibling: same cached `getEventsInRange` + `SimpleEventList` + JSON-LD spine) reads [lib/intent-pages.ts](../../lib/intent-pages.ts): per-page fixed human-written editorial + search-shaped Q&A (never LLM-generated; em-dash-free locked by `scripts/test/intent-pages.test.ts`) and a pure lens filter — `isFreeEvent` (stated-free only, mirrors the extract-prices never-guess policy) and `isDateNightEvent` (public + live_music/wine/fine_arts/festival + start ≥ 16:30). - **Artist blurbs on live-music pages** (`components/ArtistInfo.tsx`, 2026-09-12, HWY-36 / `PRD-artist-descriptions.md` Phase 2). Live music is the #1 category; Phase 1 already stored published `hwy4_artists` rows (`genre` / `blurb` / `links` / `hometown` / `is_local`) behind `/admin/artists`. Phase 2 renders them: a server `ArtistInfo` block (genre chip + published blurb + outbound links) on the event detail page for each `artists[]` name that matches a row via the same `normalizeName` key the drafter writes (`lib/artists.ts`, locked by `scripts/test/artists.test.ts`); the EventCard artists chip appends a published genre; JSON-LD `performer` upgrades to `MusicGroup` when a published row matches (bare names stay `Person`). **Tier C:** unknown or draft-only rows render nothing. Never-guess: public paths select only live columns and `toPublicArtist` drops `blurb_draft*`. Gated to `category==='live_music'`. Phase 3 `/artists/[slug]` hubs remain out of scope. **Coverage + accuracy pass (2026-10-04).** Three fixes, each where the gap was. (1) *Acts in titles:* most sources leave `artists` empty even when the title names the act, and the drafter only researches the field. `extractActFromTitle` ([lib/event-identity.ts](../../lib/event-identity.ts)) reads the corridor's real shapes ("Live Music - X", "Music In The Square- X", "... Concert Series – X", "(LIVE MUSIC - X)", "featuring live music by X", "X Live Music @ Venue") and refuses anything `isPlaceholderForMatch` reads as a placeholder, a town, a karaoke/theme night, an event head ("Vintage Car Show, Hatcher Wine & Live Music") or a multi-dash ambiguity. It fills an EMPTY list only, in `normalizeEventLocation` (every `upsertEvents` source) and in the exact-match update (`artistsFill`, which never wrote `artists` before; `artists` is now selected on all three exact-match reads). Ship-time measure: 14 of 89 actless 60-day rows filled, zero false positives, but only 1 upcoming, because Boyle MacDonald's 42 upcoming "Live Music Upstairs" rows name no act anywhere. **A fake act is not cosmetic:** `actNamedInOther` reads `artists`, so the independent review of #324 showed "Live Music with Dinner" (artists ["Dinner"]) merging with "Thursday Night Dinner". `isPlausibleAct` therefore refuses any capture holding an event/status/amenity word (`ACT_VETO_WORDS`: happy hour, cancelled, dinner, fundraiser, season finale…), any capture made only of genre/setting words (`ACT_SOFT_WORDS`: "Jazz", "Tribute Band", "All Ages"; one real name word rescues it, so "Bob Eisenman Jazz Band" passes), a region place name, or a venue-shaped tail ("… Lodge", "the Pool"). The exact-match fill is gated on `isPlaceholderForMatch` as well, and the different-acts veto in `isSameEvent` compares by `artistIdentityKey` (narrowing only: "Bad Jovi" vs "Bad Jovi Band" is one act). (2) *One identity per act:* [lib/artist-identity.ts](../../lib/artist-identity.ts) `artistIdentityKey` folds &/and, copy suffixes and ensemble suffixes (Band/Duo/Trio/Quartet/Project/& Friends) to letters+digits. It is a MATCH key, not the storage key (`artist_key` stays `normalizeName`). Deliberately not fuzzy: "Sipsy"/"Sipsey" and "Greg"/"Gregory" stay separate. `tidyArtistList` collapses variants and keeps a compound billing whole (no more "Union Station" split off "Alison Krauss & Union Station"); it runs at the write boundary and inside `mergeArtistLists`. Render paths fall back to the identity key (`artistMatchKey`, `~`-prefixed; read genres with `genreForArtist`), exact key first. (3) *Researcher context + retries:* the drafter's worklist is now the pure [lib/agent/artist-worklist.ts](../../lib/agent/artist-worklist.ts): acts grouped by identity, results land on the act's existing row, karaoke hosts/theme nights skipped, and `researchArtist` gets up to 3 bookings (venue, date, link, 400-char description, distinct venues first) so a venue can disambiguate a generic name. A tried-blank row is retried only on new evidence (`no_context` research that predates this, `new_venue` against the UNION of every venue it was ever researched with, `voice_retry` once when the em-dash/banned-phrase floor dropped prose for an identified act, e.g. Deep Thicket Dwellers) or after `RETRY_AFTER_DAYS` (60); never-researched acts go first, and a row with any live blurb/genre/links is never retried. Meta gains `context_venues` / `voice_rejected` / `voice_retried` / `reason`. One-time cleanup: `cd scripts && npx tsx backfill-artists.ts [--all] [--catalog] [--apply]` (events fill + tidy; `--catalog` supersedes a variant's pending draft into `blurb_draft_meta.prior_draft` + `superseded_by`, reversible). Locked by `scripts/test/artist-identity.test.ts`, `artist-worklist.test.ts`, `artists-fill.test.ts`, `artists.test.ts`.
